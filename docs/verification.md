# 完了条件から検証する

設定済みチェックの成功は、そのチェックが確かめた範囲の証拠である。依頼の達成は、依頼の各条件と観測を対応付けて判断する。`da-verify` はチェックの結果と、その対応を併記する。書き方の正本は [完了条件と証拠](../skills/da-verify/reference/acceptance-evidence.md)。

## 固定課題を再実行する

```bash
node scripts/lib/evaluate-gate.mjs --output /tmp/dotagents-proof-001
```

出力先は存在しないディレクトリを指定する。正常版と3つの故障版を、同じ7つの課題へ通す。対象は checkout 内の `scripts/gate.sh` と `hooks/dotagents-verify-gate.sh` だけで、インストール済み hook を編集しない。一時 git リポジトリ・profile・ゲート状態を作り、実スクリプトを実行する。ネットワーク接続も追加依存も不要。

- `report.json` は期待と観測、終了コード、課題ごとの成否、誤通過・誤停止、検出した故障、所要時間、対象と評価器の SHA-256 を持つ。
- `baseline/` と各故障版のディレクトリは、各課題の入力・準備・コマンド・標準出力・標準エラーを持つ。
- `target/` は実際に読んだ正常版のスクリプトと評価器を保持する。作業用の git リポジトリは削除しても証拠は残す。入力版が壊れていても観測結果を残し、非0で終了する。
- 正常版が全課題を満たし、すべての故障を適用できて検出した場合だけ終了0。故障を適用する箇所が変わった時は、検出成功に数えず、評価器の見直しが必要になる。

保存された実物を再評価する場合:

```bash
node /tmp/dotagents-proof-001/target/scripts/lib/evaluate-gate.mjs \
  --output /tmp/dotagents-proof-002
```

別の checkout を同じ課題で比べる場合:

```bash
node scripts/lib/evaluate-gate.mjs --source /path/to/other-checkout \
  --output /tmp/dotagents-proof-other
```

評価器が指定先のスクリプトを実行するため、信頼する checkout だけを対象にする。比較では評価器のハッシュを揃える。ハッシュが違う測定は手順も変わっているので、製品だけの改善と数えない。時間には機械・OS・負荷の差が含まれ、1回の値で速度改善を主張しない。

## 機能と証拠の対応

これは検証マップで、実行済みを示す台帳ではない。各実行の結果は出力先の JSON と検査ログで確認する。

| 利用者の操作・完了条件 | 再実行する入口 | 観測する結果 | この観測で分からないこと |
|---|---|---|---|
| インストール・更新・解除で他人の設定を保つ | `scripts/test-setup.sh` | 隔離した設定ファイルの値・コピー・リンク | 各ホストがその設定を実際にロードしたか |
| 掛けていないセッションを止めない | 固定課題 `unarmed` | exit 0、検査の副作用なし | ホストの hook 呼び出し有無 |
| 掛けたゲートで検査を実行し、正常時に通す | 固定課題 `green` | exit 0、検査が書いたファイル | 機能固有の受け入れ条件 |
| 赤なら終了を止める | 固定課題 `red` | exit 2、検査が書いたファイル | Claude Code・Codex の実アプリが終了を拒否したか |
| 人に頼んだだけの検査を緑にしない | 固定課題 `delegated` | exit 2、委譲したコマンドの副作用なし | 実際の人が行ったチェックの正しさ |
| profile 不一致を検証成功と混同しない | 固定課題 `no-profile` | `checked: false`、`profile: null` | エージェントが報告を正しく解釈したか |
| 変更を受け持つ検査がなければ通さない | 固定課題 `uncovered` | exit 1、`kind: not_checked`、副作用なし | profile の検査内容自体が十分か |
| Cursor の赤で続行を促す | 固定課題 `cursor-red` | 非空の `followup_message`、検査が書いたファイル | Cursor が実際にメッセージを送信・続行したか |
| 再試行上限・期限・worktree の状態を扱う | `scripts/test-verify-gate.sh` | 状態・記録・終了コード | 状態遷移を全順序で網羅した証明 |
| 証拠を後片付け後も読める | `scripts/test-verification-evidence.sh` | 生出力の実在・保存した対象での再実行・上書き拒否 | 長期保存先の管理・閲覧権限 |

**ホスト内での確認は別に行う。** Claude Code・Cursor・Codex それぞれで、スキルが見つかる→呼ばれる→ゲートが掛かる→赤の応答をホストが処理する→修正後に解除される、まで観測して初めて、そのホストでの経路を確認済みとする。ペイロードをCLIで入力した結果だけでは代用しない。実アプリの確認結果と日付は [ハーネスの確認記録](harness-facts.md) に残し、今回の固定課題から確認済みへ更新しない。

## 保守と限界

変更前後の観測とテストの限界は [2026-11-15の比較記録](evaluations/2026-11-15-verification-evidence.md) に残す。

機能・入口・前提が変わったら、影響する行と完了条件を見直し、対応する操作を再実行する。期待と違う動作は、製品の回帰・手順の陳腐化・環境不足に分ける。正しい仕様の根拠なしに期待値を実装へ合わせない。

故障版は「拒否の終了コードを消す」「未検査の変更を受け入れる」「Cursor の応答キーを壊す」の3つに限る。検出できても他の故障を捕まえる証明にはならない。AIレビューの誤検知・見逃し・費用はこの評価では測らない。これまでの指示比較の限界は [レビュー所見の比較記録](evaluations/2026-11-14-review-evidence.md) にある。

形式検証の最初の候補は、arm・disarm・期限切れ・再試行上限と、worktree 間の状態分離。着手時には、原子的な操作と実装の対応、時刻と並行実行の仮定、探索上限を定める。反例を実スクリプトで再現し、壊した実装も検出してから結果を採用する。今回の固定課題はモデル検査でも形式証明でもない。
