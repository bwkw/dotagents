# ソフトウェアファクトリーで何を検査するか

2026-11-28 に開発者自身の報告を調べた。dotagents への提案は、依頼ごとに一つの入口を選び、同じ完了条件を設計・実装・検証の間で引き継ぐこと。反復の駆動には既存の `scripts/loop.sh` を使い、新しいスキルは検査を整備する仕事を引き受ける。[既存ループの工程と台帳](../loops.md)

## 各事例から採る判断

| 何を見分けたいか | 開発者が報告したこと | dotagents へ適用する条件と限界 |
|---|---|---|
| 既知のテストに合わせ込んだ変更を見抜けるか | StrongDM は、利用者のシナリオをコードベースの外にも置き、実環境に近い経路で評価し、その結果を次の実装へ返している。[開発チームの報告](https://factory.strongdm.ai/)・[評価と反復の原則](https://factory.strongdm.ai/principles) | 判断が難しい受け入れ条件は、実装前に利用者の操作と期待結果を固定する。高い独立性が必要なら、実装担当に渡す例と最終判定に使う例を分ける。現行ループが検知できるのは、保護対象に指定した採点ファイルの変更までである。[採点対象の変更検出](../../scripts/loop.sh#L245) |
| 実装者が自分で挙動を観測できるか | OpenAI の社内ベータでは、作業ツリーごとにアプリを起動できるようにし、画面、ログ、指標をエージェントから読めるようにした。短い案内からリポジトリ内の詳細へ進む文書構成も採った。[開発者の記録](https://openai.com/index/harness-engineering/) | 検査を書く入口は、実物を動かすコマンド、入力、観測箇所、後片付けを対象プロジェクトに残す。実行する入口は今回の観測を返す。CLI で生成した応答だけを根拠に、各ホストの画面でも動作したとは報告できない。[現行の検証範囲](../verification.md#L34) |
| タイミング次第で変わる失敗を再度観測できるか | FoundationDB は時計やネットワーク等を制御する実行環境を作り、同じスケジュールを再現して、失敗後に計測点を追加できるようにした。[開発チームの技術解説](https://apple.github.io/foundationdb/engineering.html) | 実コードの再試行やタイムアウトを検査する時は、再現に必要な入力・時刻・順序を保存する。シミュレーションで制御した環境条件を報告し、実環境に残る観測を別に扱う。最初は対象の障害一件を再現できる範囲で足りる。 |
| 普通のテストで選びにくい操作順があるか | AWS の設計者は、DynamoDB の複製設計で、不具合を示す最短の実行列が35ステップに及ぶ例を報告した。別のロック管理の事例では進行性を検査対象から外し、その種の不具合を見逃している。[設計者による論文、表と DynamoDB の事例](https://www.cl.cam.ac.uk/teaching/2021/HLog%2BModC/How-Amazon-Web-Services-Uses-Formal-Methods.pdf) | 並行操作や復旧順が論点の時は、状態・操作・守りたい性質を小さなモデルにする。「不正な状態に入らない」と「いつか先に進む」は別々に記録し、探索範囲と未検査の性質を結果に残す。 |
| モデルの反例は実装にも当てはまるか | mizchi 氏は、Quint で見つけた単一書き込み制約の反例を Rust の公開インターフェースに与え、修正前の実装でも違反を確認した。[著者の実験記録](https://zenn.dev/mizchi/articles/quint-application-modeling) | 設計レビューではモデル上の反例を所見にできる。実装の欠陥と判定する時は、同じ条件で実装側の観測を加える。残す価値がある反例は再実行できる回帰検査へ移す。 |
| 増え続ける業務規則から判断が導けるか | freee のエンジニアは受付の業務規則を Lean で表現し、会話ごとの判断の導出を機械検査した。記事の集計時点では開発用74課題中45課題で満点かつ証明が完了し、評価用23課題の測定は今後の課題だった。[著者の実験と評価範囲](https://developers.freee.co.jp/entry/lean-formal-verification-ai-agent-guardrails) | 人が確認できる命題、信頼する入力、使った公理を残せる場合に定理証明を使う。入力の読み違い・規則の転記誤り・実システムでの副作用は、それぞれ別の観測を要する。 |

## dotagents での最初の使い分け

- **設計レビュー**で「同じリポジトリの作業ツリー A の失敗が B の再試行回数を消費しない」という性質を調べる。モデルに含めた操作と二つの作業ツリーの範囲を示し、順序の反例があれば設計者に返す。[既存の対象候補](../verification.md#L61)
- **検査を書く時**は、この性質をすでに観測するテストを調べ、必要な順序だけを追加する。元の実装と、回数を誤って共有する故障版に同じ操作を与え、終了コードと実際の試行状態を比較する。検査が仕様を守る実装まで落とす場合も修正対象にする。[既存の固定課題と故障評価](../verification.md#L5)
- **変更を出す時**は、プロファイルが許す検査を実行し、観測を依頼の完了条件に対応付ける。利用者の判断が必要な所見や未検証の状態は台帳に残す。これにより次の担当者は、同じ実行を繰り返すか、仕様を見直すかを判断できる。[検証結果の解釈](../verification.md)・[反復を止める条件](../loops.md)

各事例は、異なる製品と評価条件での一次報告である。dotagents における手戻りの変化は、旧入口と新入口に同じ依頼を与え、選ばれた経路、故障の検出、誤って通した件数を比較して評価する。
