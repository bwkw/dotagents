# retro の本文比較（2026-10-26）

## 何を確かめたか

通常の依頼で足りるか、上流の `retro` を使う価値があるか、自前の `da-retro` が必要かを比べた。合成した 1 ケースを各条件 1 回ずつ、別のセッションで実行した探索的な比較である。実案件での性能やトリガー精度のベンチマークではない。

モデルは親セッションから継承し、固定や条件別の変更はしていない。全条件に同じ作業記録と同じリポジトリを渡し、読み取りと日本語の提案だけを求めた。各評価者には他の結果・期待する改善案・採点項目を渡していない。通常条件は専門スキルなし、スキル条件は指定本文を明示して読むよう依頼した。自動発火・Skill ツール・実際の依存の名前解決は測っていない。

| 条件 | 渡した指示 |
|---|---|
| 通常 | 専門スキルを使わず、作業記録の依頼に回答 |
| 自前 | 先に作成した `da-retro` 本文を使って同じ依頼に回答 |
| 上流 | `retro` と必須依存 `writing-for-agents` の本文を読んで同じ依頼に回答 |

上流は [mattpocock/skills@5beb35b](https://github.com/mattpocock/skills/tree/5beb35b040e3de97e54fa9e386d7e42d15c295c2) の本文。自前版は前の作業で作成して今回撤回した版で、本文の SHA-256 は `514146b616f05636d0ed9877d424c17c59f62943d6eb420548c2ba144c7351a7`。上流の振り返り観点を日本語化し、別スキル呼び出しを外し、読み取り専用・根拠・停止条件を足したものだった。

## 入力

対象リポジトリには次の 6 ファイルだけを置いた。全条件は必要に応じて読めるが、すべてを読むこと自体は強制しなかった。

| ファイル | 内容 |
|---|---|
| `AGENTS.md` | 動的な文字列実行は禁止。検証は Makefile の `check`。規約を足す前に既存検査を確認する |
| `Makefile` | `check: lint test`。lint は `node scripts/lint.mjs`、test は `node --test tests/*.test.mjs` |
| `scripts/lint.mjs` | `src/calculate.mjs` を読み、正規表現 `\beval\s*\(` に一致すればエラーを表示して終了コード 1 |
| `src/calculate.mjs` | `calculate(x, y)` が和を返す、修正後の実装 |
| `tests/calculate.test.mjs` | `calculate(2, 3)` が `5` であることを確かめるテスト |
| `.github/workflows/ci.yml` | push・pull_request で checkout と Node 24 の準備を行い、`make test` だけを実行 |

作業記録は次の内容。

1. 計算式入力の依頼に対し、エージェントが `npm test` を実行したが package.json がなく失敗。Makefile を読み `make test` で成功した。
2. `eval(expression)` を使った変更案のテストは通ったが、ユーザーが既存の禁止規約を指摘した。`make check` は違反を検出し、修正後は成功した。同種の違反は記録上この 1 回だけ。
3. エージェントは専用の新しい禁止 API チェックと常設の注意書きを提案したが、まだ適用していない。
4. 別の HTTP テストがソケット制限下で失敗し、制限外では成功した。エージェントは非同期テストの禁止を提案したが、適用していない。
5. 外部サービスの仕様に接続できず、API 契約を確認できなかった。ユーザーは全サービスの管理者権限に同意していない。

依頼文は「この作業を振り返り、次の開発を良くする環境の改善案を、実際の根拠があるものだけ優先順に提案して。既存の検査や指示で足りるならそれを使いたい。今回は提案だけで、ファイルや外部の設定は変更しないで」。

通常条件は既存の `make check` を提示前に実行することを第 1 案とし、環境制限と読み取り情報の不足も区別した。CI の呼び出し変更は出なかった。

自前条件と上流条件は、どちらも CI の `make test` を既存の `make check` に揃えることを第 1 案にした。新しい lint や注意書きは不要とし、外部仕様には限定した読み取り手段を提案した。自前条件は各案の確認方法を表にしたが、この比較では独自の有用な改善案の増加は観測しなかった。

## 反対側の評価と限界

別の評価者が、先行の採否表を見ずに候補を読んだ。最初は「新規標準導入なし。retro は比較してから保留判断」とし、比較結果を渡した後も「自前版の撤回は支持。上流版は採用候補だが即時導入は保留」と判断した。

理由は、上流の必須依存がスキルや常設指示の執筆時にも発火するため、振り返りだけを人が呼ぶ小さい追加に閉じないこと。3 ハーネスの依存解決、実案件での改善案の採用率、執筆への影響が未確認なことだった。

ただし、この評価の採点者は条件名を知っており盲検ではない。モデルの確率的な揺れ、読んだファイルの選択、出力の長さによる差を分離していない。時間・トークン・実際の改善案の採用は測っていない。1 件 1 回なので、一般の精度差や上流版と自前版の同等性を証明するものではない。

今回の判断は「自前版の採用根拠が足りない」「上流版にも副次的な影響があり、いま常設導入する根拠は足りない」まで。必要になった実案件で上流版を先に試す。採否全体は [外部スキルの評価](../external-skills.md) を参照。
