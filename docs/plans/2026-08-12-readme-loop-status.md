## なぜ tier L だったか（そしてそれを尊重する）

`size` は **1 file・0 layers・one-way 0・risk surface 0・unconfirmed 9** で L を出しました。**ファイル数でも
レイヤ数でもなく、`unconfirmed 9` が上げています。**

原因は変更の規模ではなく**依頼文**です。依頼が「台帳に `pr` / `fix` / `findbugs` が1回も無い」「テスト件数を
更新する」と、**確認の要る主張を含んでいた**。調査器はそれを確認できないので unconfirmed に挙げます。

**これは `unconfirmed` の2つ目の実測で、フィールドがまだ2つのものを混ぜていることを示しています** ——
「変更の規模を測れなかった」と「依頼が検証の要る主張を含む」。段の規則が気にするのは前者だけです。
**ただしここでは規則を曲げません。** 判定は L で、設計フェーズはこの文書です。

## この計画が明示的に禁止すること

- **`README.md` 以外を触らないこと。** 特に `docs/loops.md` は #38 が同じ節を触っているので、
  ここで触ると衝突します。
- **コストの数字を推測で書かないこと。** `scripts/loop.sh report` を実行し、その出力を使うこと。
  出せないなら、数字を書かずに「台帳を読め」とだけ書くこと。
- **「ループは完成した」と書かないこと。** PR を開く3段は未実証で、それを緑に見せる文は、この
  リポジトリが繰り返し捕まえてきた失敗そのものです。

## 過去形のプリモーテム

ブロックが「未実証」と言い続けている。**防ぎ方は、数字ではなく出どころを書くこと** ——
「`scripts/loop.sh report` を読め」と書いてあれば、文が古びても読者は正しい場所に行けます。
