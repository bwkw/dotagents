## 決めたこと

### 1. 所有者で経路を分ける

`review-process.md:13-27` に「whose change is this」の判断はあるが、**dispatcher がそれで何も分岐していない**。
Step 1 で判定し、他人の PR なら成果物を入れ替える。自分の変更・PR 無しは現状どおり。

### 2. 成果物はホストで分岐、中身は同一

Claude Code → Artifact、Cursor → Canvas、どちらも無い → HTML ファイルを書いてパスを出す。
**6 節の構成は 3 つとも同じ**。器の選択が中身を変えないようにする。

### 3. 層レポートは出力しない。honesty 機構だけ救出する

落とすと壊れるのは 🔎（読んだもの / 仮定したもの）と 🔬（反証件数・閾値未満で落とした件数）の 2 つだけ。
これはアーティファクトの節へ移す。**所見の完全な記録は落とす** —— ただし `pr-comments.md` の選別ロジックが
「落としたものもレポートに残っている」を前提にしているので、そこも同時に直す。

### 4. クリティカルな観点をサンプリングの外に出す（中核）

いまは Step 1b が「1,000 行超はサンプル」と言い、Step 5 が「浅さは 🔎 に告白すれば良い」と言う。**告白すれば
許す設計**になっている。

**アーキテクチャ適合はファイルを読む作業ではなく `grep` と配置の照合なので、10,000 行でも全数でやれる。**
読解のサンプリングと同じ土俵に置いていたのが間違い。Step 2（影響範囲マッピング。既に必須・読解前）に
**Step 2b「規約適合の全数確認」**を足し、サンプル宣言は**意味的な読解にだけ**適用すると限定する。

全数で見るもの: リポジトリ自身のアーキテクチャ規約への配置適合 / 依存の向き / 不可逆面 / テナント境界 /
新しい書き込み入口と非同期経路。

### 5. 口調プロファイルを他人 PR と判定した時点で読む

### 6. 出力予算を契約にする —— 同じ所見を 2 か所以上に書かない

| 置き場 | 書くもの |
|---|---|
| アーティファクト | 全体感 + 決めごと + 🔎🔬 |
| コメント案 | 所見（PR に出すもの） |
| ターミナル | 索引だけ |

### 7. 投稿まわりの実務を `_shared/pr-comments.md` へ

アンカーの事前検証 / 積み PR のファイル→PR マッピング / `gh api` はフルパスで叩く / 投稿後に
`position != null` を確認。**`_shared` なので 3 層すべてに効く。**

## 触らないもの

`perspectives.md` の観点そのもの、`finding-discipline.md`、敵対的検証、1,000 行超のサンプル宣言（読解に
限定はするが規則自体は残す）。**`profiles/review-voice.md` も触らない** —— 実例 27 件から作られていて
「食い違ったら実例が勝つ」と書いてある文書に、実例でないものを足すのは筋が悪い。
