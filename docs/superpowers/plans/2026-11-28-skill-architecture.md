# 開発スキルの入口と構成

**設計・配布日**　2026-11-28。対象は dotagents が配るスキルと、README が選択導入を案内する上流スキル。現在のインストール手順は [README](../../../README.md) にある。

利用者が選ぶのは「何を持ち帰りたいか」までとする。テストの種類、レビューの層、並列数、図の描画器は、対象を読んだ後で入口が選ぶ。どの入口でも、依頼から読み取れる成果、変更してよい対象、終わりを判定できる証拠を先に定める。

## 普段使う6つの入口

| こう頼む | 名前 | 受け取るもの | 中で選ぶこと |
|---|---|---|---|
| 「今どう動く？」「なぜこの判断をした？」「障害の原因を知りたい」 | `da-investigate` | 根拠のある答えと未確認事項 | 動作は呼び出し経路、来歴はコミット・PR・ADR、障害は観測と再現、外部仕様は一次資料へ。調査結果のファイル保存は依頼がある時だけ |
| 「これを設計したい」「仕様に残して」「このレビューを修正計画にして」 | `da-plan` | 合意したい選択肢、仕様、または順序のついた修正計画 | 相談は会話で選択肢と推奨案まで。仕様の作成・更新は `spec_system`、所見の整理は既存の修正計画の規則と保存先を使う。依頼文の推敲なら書き直した依頼文で完了 |
| 「作って」「この不具合を直して」 | `da-implement` | 動く変更、先に失敗したテスト、実行結果 | 機能追加は利用者の操作を通るテストから、不具合は再現と原因特定から。既存計画があればそれを使う。独立に検証できる作業だけ分割し、単純な変更は一人で完了する |
| 「この設計をレビューして」「このPRを見て」 | `da-review` | 根拠と重要度の付いた所見 | 設計なら不可逆な判断・移行順・着地の表。差分なら意図の再構成・層別と層間の検査・反証。設計と差分の両方が指定されたら、設計上の懸念と実装での充足を対応づける |
| 「今の変更は出せる？」「このチェックを回して」 | `da-verify` | 設定済み検査の結果と、完了条件ごとの証拠 | 一致するプロファイル、変更範囲、実行権限で選ぶ。検査で覆っていない条件も報告する。性能改善を主張する時だけ、実処理・失敗数・反復・実利用との対応を点検する |
| 「この条件を毎回検査したい」「実装が変わったので検査を直して」 | `da-write-checks` | 再実行できる検査、対象範囲、検査自身が故障を検出した記録 | 対象に既存検査があれば拡張する。実操作、生成入力、状態探索、定理証明から必要な手段を選び、運用するリポジトリに置く |

`da-implement` が引き受けるのは、依頼とテストと変更を対応させる判断である。計画実行、作業隔離、コード生成を順番に全部起動する入口にはしない。複数の変更をPRまで追跡する依頼では既存の `scripts/loop.sh` と台帳を使う。リリース後の不具合も、まず `da-investigate` が実際の障害記録・変更履歴を読み、修正を頼まれたら `da-implement` に同じ再現条件を渡せる。

たとえば「二重送信が心配」だけなら、設計中は「どの操作順で起きるか」を `da-review` の所見として返す。「二重送信を検出するチェックを残して」なら `da-write-checks` が同じ操作を使う回帰検査を作る。「二重送信を直して」なら `da-implement` が失敗する回帰テストから修正まで進める。最後の依頼に対して、利用者に3つのコマンドを順々に打たせる必要はない。

## 特定の成果物や保守に使う3つの入口

| こう頼む | 名前 | 内部の選択と境界 |
|---|---|---|
| 「この判断をADRに残して」 | `da-adr` | 決定・理由・捨てた案を、プロファイルが定めた保存先へ。既存ADRの更新と新規作成を区別する。画像を置ける保存先では共通のADR図生成を使う |
| 「PR本文を整えて」「この2件でGreptileに何を見てほしい？」 | `da-pr` | 既存PR向けの本文またはレビュー依頼文を作る。下書き、本文更新、コメント投稿を区別し、対象と内容に対応する指示がある操作だけ行う。自分で所見を出してほしい時は `da-review` |
| 「スキルを足す価値がある？」「候補を安全に入れられる？」 | `da-skills-audit` | 重複・予算はファイル監査、第三者の候補は静的検査、効果は同じ依頼での比較実行。結果はそれぞれの根拠と限界を添えて返す |

資料生成は内部の `x-present` に置く。ADRからは図解の経路を呼ぶ。動画だけの依頼には録画の経路がある。ADRは確定した判断を後から追える記録で、計画はこれから行う変更の合意に使う。図だけを頼まれた時は元のADRを編集しない。PRの読み取りで始まったレビューは、設計やコードの修正、GitHubへの投稿を暗黙には引き受けない。既存の行コメント案・投稿フローの明示指示も移行テストに含める。

## 名前の判断

- **`da-write-checks`** を推す。「書く」は初めて書く時にも、陳腐化した検査を書き直す時にも使える。`da-verify-setup` は初期設定に見え、プロファイル設定とも紛れる。`da-test` は実行と作成の両方に読める。`da-verify setup` は既存のチェックID引数と競合する。「今チェックして」は `da-verify`、「繰り返せるチェックにして」は `da-write-checks` と言い換えられる。
- **`da-review`** は設計とコードに共通する依頼の動詞。既存の `all` や層名を覚える必要をなくす。入力の種類を失うと返すべき所見も変わるため、既存の設計レビューと差分レビューの本文は別の分岐にする。
- **`da-plan`** は相談・仕様・修正計画を包含する。**`da-adr`** と **`da-verify`** は短く、成果物や操作が既に明確なので継続する。命名の統一だけを理由にした改名はしない。

## スキルの中身の分け方

| 置き場所 | 受け持つもの | `da-review` での例 |
|---|---|---|
| 公開する `SKILL.md` | 依頼例、実行条件、読むファイル、分岐条件、出力、終了条件。分岐前に全手順を読まない | 対象が設計書・差分・両方のどれかを決め、所見を返す |
| 入口固有の `reference/` | 選ばれた経路だけで使う手順と具体例 | 設計を読む時だけ着地の表と移行順を読む。差分を読む時だけ変更規模・層・概要出力の契約を読む |
| `skills/_shared/` | 複数の入口で同じ意味を持つ規則の正本 | 観測と推論を区別する所見の規律。層固有の観点は層の参照先に置く |
| `x-*`・上流スキル | 独立して実行する理由と実際の呼び出し元がある仕事 | 層別3本は自動呼び出し可能なまま。大きい差分の反証は専用の役が担当し、モデルはセッションから継承する |
| スクリプト・プロファイル・hook | 決定的に実行・判定できること、プロジェクト固有のコマンド、強制する条件 | チェックの実行権限と合否は既存ゲートが判定する。レビュー本文に同じ判定処理を作らない |

README の「何をしたいか」には依頼と入口を載せる。実際の分岐は各 `SKILL.md` に置く。参照先を本文から `${CLAUDE_SKILL_DIR}` で解決し、自作スキルは日本語・本文12 KB以下・`metadata.source: bwkw/dotagents` を維持する。共有規則は既存のリンク方式で配る。第三者の本文は上流で保守する。手動専用の上流スキルを自動呼び出し経路に組み込まない。必要な機能が実行ファイルとして配られている時は、導入済みの版と実行可否を確認して使う。[不変条件](../../../AGENTS.md)・[仕組みの選び方](../../mechanisms.md)

たとえば `x-present` はPNGを選んだ時だけ図の形式と描画スクリプトを読む。ADRからも同じ処理を呼ぶ。動画ならシナリオ、録画、字幕・音声、再生確認の経路を読む。特定の形式を指定され、その手段が無い場合は不足を返す。この粒度なら、描画器を替えても入口の名前やADRの記録方法には波及しない。

## 検査を書く入口で、どこまで引き受けるか

1. 「何が起きたら利用者との約束が破れるか」を1文にし、その根拠となる仕様や実装を示す。すでに検査がある時はその範囲と実際の失敗を先に確かめ、重ねて作る費用を避ける。
2. 通常の操作で見える性質は実操作・結合テスト、入力の組み合わせは実コードへの生成入力、順序に左右される性質は小さい状態モデルを選ぶ。既存のTLA+があれば活かし、Quintのモデルがあればそちらを使う。新規なら維持担当が再実行できる方を選ぶ。入力上限のない命題の証明が必要で、前提を定義できる場合に Lean を選ぶ。[手法の違い](https://zenn.dev/ncdc/articles/dcec80b0c067b0)・[pstack の選択基準](https://github.com/cursor/plugins/blob/bf0c7cd80abdbf7fe47b634978a7d1b4071f71a7/pstack/skills/create-formal-verification-skill/SKILL.md)
3. 状態探索では、時刻・並行性・原子的とみなした操作と探索上限を記録する。反例は実装で観測を試み、モデルだけでの反例と区別する。証明では命題・前提・外部から得た事実・実装との対応を人が確認できるようにする。証明の未完了を許す記述や、説明の付かない追加公理も検査する。[Quint による実装との照合](https://zenn.dev/mizchi/articles/quint-application-modeling)・[freee の業務規則と証明の境界](https://developers.freee.co.jp/entry/lean-formal-verification-ai-agent-guardrails)
4. 再実行コマンドと対象箇所、対応を確認した版を残す。壊した版で期待した理由で失敗し、元に戻すと基準の結果に戻ることを確かめる。実装がすでに違反していた場合は所見を残す。更新時は仕様の変更、検査と実装のずれ、実装の回帰、実行環境不足を区別する。[pstack の保守手順](https://github.com/cursor/plugins/blob/bf0c7cd80abdbf7fe47b634978a7d1b4071f71a7/pstack/skills/maintain-formal-verification-skill/SKILL.md)

生成物の最小単位は、対象リポジトリの既存形式で実行できる検査1件。プロジェクト用スキルの生成は、複数の操作・証拠保存・後片付けまで次の担当者に引き継ぐ場合に限る。`da-write-checks` は検査を整備し、`da-verify` が登録済みチェックを実行する。ゲートを arm する経路を増やさない。[現行の検証契約](../../../skills/da-verify/SKILL.md)

## 移行で確認したこと

- **配布。** 隔離した環境で旧版からの更新、再実行、管理外スキルの保持を検査した。実際の配布先2か所では旧名8本が消え、13本が現在のスキルを指す。コピーしたhookも原本と一致した。Codexの一覧は13本、Claude Codeの直接入力一覧は公開9本と単一層の無人レビューに使う3本を確認した。
- **成果物。** PRは実際の小変更を2行、構造変更を図1枚と確認箇所で説明した。本文更新は隔離したGitHub CLIで、対象・下書き・反映結果を照合した。ADR図と動画は各生成器で検査した。[PR本文の実例](../../../skills/da-pr/reference/pr-template.md)
- **形式検証。** 作業ツリー間の試行回数を小さなTLA+モデルで検査した。回数を誤って共有させた版では、モデルの反例を実際のhookでも再現した。[実験条件と再実行手順](../../verification.md#作業ツリーごとの試行回数を検査する)

## 比較を残したもの

3ホストの自然文による選択精度、通常の実装依頼と `da-implement` の成果の差、実アプリ用の上流2本を置き換えられるかは未計測。比較には「このPRを見て／このPRの説明を書いて」「検査を回して／再発を検出する検査を残して」などの対を使う。成果物、許す操作、故障を検出する条件を先に固定し、実アプリでは操作手順が変わった後の保守まで試す。個人が導入した上流はその結果を見て削除を判断する。
