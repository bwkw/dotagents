# 完了条件と実行証拠の改善計画

目的は、設定済みチェックの成功と依頼の達成を区別し、検査が故障を捕まえることを再実行可能にすること。
既存のゲートを合否の正本に保ち、新しいスキルや別の arm 経路は作らない。追加依存は使わない。

## 1. 固定シナリオと故障注入

- [x] `scripts/test-verification-evidence.mjs` に、実ゲートの観測・故障検出・出力保持を確かめるテストを書く。
- [x] 新しい評価器が無い状態でテストが失敗することを確認する。
- [x] `scripts/lib/evaluate-gate.mjs` で、一時 git リポジトリと実スクリプトを使う評価を実装する。入力と期待値は固定し、終了コードだけでなくチェックの副作用・応答・未検証状態を観測する。
- [x] 正常版と故障版を同じシナリオに通し、誤通過・誤停止・検出した故障・所要時間・対象ハッシュを JSON に残す。既存出力の上書きは拒否する。
- [x] `scripts/test-verification-evidence.sh` から実行し、`check.sh` と profile の両方に接続する。

## 2. 完了条件と利用経路

- [x] `da-verify` から必要時に読む参照へ、完了条件・入力・期待・観測・証拠・未確認の対応表を置く。元の期待値を、観測に合わせて弱めない。
- [x] dotagents の機能マップに、CLI で実証する範囲と各ホストで未確認の範囲を明記する。製品の回帰、手順の陳腐化、操作手段の不足を分ける。
- [x] 形式検証は対象候補と前提を記す段階に留める。今回の固定シナリオを網羅的な状態探索や証明と呼ばない。

## 3. 評価と検証

- [x] 比較コマンドと生出力を保持する。AI の誤検知率・見逃し率・費用は測定していないと明記する。
- [x] `da-verify` で profile のチェックを実行する。既存の `.venv` 等による失敗は、元の状態から分けて報告する。
- [x] README と判断の記録を更新する。既存の未コミット変更は保持し、コミット・インストール・外部投稿は行わない。

## 4. 終了ゲートで確認した生成物の誤検出

- [x] 依存物を置いたまま通るケースと、同じ不備を本物の参照へ置くと拒否するケースを先に追加し、前者だけの失敗を確認する。
