# 判断の記録

ADR 7本を1本に畳んだもの。**現在有効な判断**と、**間違えて反転させた判断**だけを残しています。畳んだ理由は、0003 を 0005 が修正し、0004 を 0006 が部分反転し、0005 の一部を 0006 が範囲縮小していて、**1つの判断の現状を知るのに4本読む必要があった**こと。

各項目は「何を決めたか / なぜ / 代償」で書きます。代償の欄が空のものは、代償を測っていないという意味です。

---

## 1. 配布はグローバル1箇所、`~/.agents/skills/`

**プロダクトリポジトリには1ファイルも置きません。** これが全体を規定している制約で、他の選択肢を全部消しています。だから配布はグローバル一本になり、Claude Code へは symlink を張ります。

**Cursor は `~/.agents/skills/` をネイティブに読みます**（実機確認済み）。`~/.cursor/skills/` へのリンクは作りません —— 作っても二重登録はされませんが、買えるものが何も無い。

**代償**: リポジトリ固有のスキルが書けません。プロダクトリポに置けないので、全部グローバルに載るか、載らないかのどちらか。

## 2. hook は symlink ではなくコピーして配る

symlink が切れると hook は `exit 127` を返し、**Claude Code はそれを non-blocking として扱います** —— ガードレールが「止まる」のではなく**「開く」**。コピーは切れません。

具体的な壊れ方: dotagents の checkout を hook が無いブランチに置く、あるいは移動する。それだけで全 hook 呼び出しが 127 を返し、**セッションは正常に見えたまま**ガードレールが効かなくなります。

**代償**: hook を編集しても `setup.sh install` を再実行するまで反映されません。`setup.sh doctor` が「インストール済みのコピーが元と違う」と報告します。

## 3. 挙動は本文に書く。frontmatter はその上の最適化

**Cursor が読む frontmatter は `name` / `description` / `paths` / `disable-model-invocation` / `metadata` だけ**で、それ以外は拒否ではなく**黙って無視**されます。

だから規則はこう: **Claude 専用フィールドを全部剥がしても、スキルは同じ挙動をしなければならない。** 制約は本文に散文で書き、frontmatter は上乗せの最適化として扱います。

`allowed-tools` を「読み取り専用の保証」として使えないのはこれが理由です。Cursor では無視されるので、読み取り専用は**本文の太字宣言**で担保しています。

## 4. `disable-model-invocation` の禁止は「名指し委譲の対象のみ」

当初は全面禁止にしていましたが、**範囲を絞りました**。このフィールドはモデルの自動発火だけでなく**プログラムからの `Skill` 呼び出しと subagent へのプリロードも止めます**。つまり:

| スキル | DMI | 理由 |
|---|---|---|
| `da-pr-describe` | **付ける** | GitHub に書き込むので、タイミングはあなたのもの。description が context から完全に消えるので予算コストもゼロ |
| `da-verify` | **絶対に付けない** | ゲートを arm する唯一のもの |
| `x-review-{backend,frontend,infra}` | **絶対に付けない** | `da-review-all` が**名前で**委譲する。付けるとディスパッチが**無音の no-op** になり、「層はレビュー済み」と報告して何もレビューしない |

lint hook とリンタの両方がテスト付きで強制しています。**リンタ側は一度、`$name` ではなく `$id` を照合していて何も検査していませんでした** —— `$id` は `skills/<name>` なので `case "$id" in verify)` は永遠に一致しない。ガードレールが設置済みで無効という状態だったので、`scripts/test-lint-hook.sh` を書いて回帰を止めています。

## 5. 層別レビューは reference ファイルではなくスキル

一度 reference ファイルに畳んで、3つの劣化を起こして戻しました:

1. 入口が3つ消えた
2. 無音事故パターンが verify フェーズにしか残らず、**find フェーズが読まなくなった**
3. 姿勢が使用箇所から2ホップ離れた

**②③ は誰にも報告されないまま起きていました。** これが「スキルを reference に畳む」ことの本当のコストです。重い観点クラスタは各スキルの `reference/` に残すので、context 経済は保たれます。

## 6. レビューの入口はメニュー上1つだけ

`da-review-all` が唯一のメニュー項目。層別3本は `user-invocable: false` で `/` から消え、**モデルからは呼べるまま**です。「backend をレビューして」と言えば description 一致で層別が直接発火するので、**失うのは「打つ」経路だけ**。

判断 5 を部分的に反転させていますが、**5 が直した不満は「深さの喪失」であって入口の数ではなく、深さは層別スキルに残っています。**

実績は層別 51回 対 `review-all` 6回で層別が主入口でしたが、メニューを小さくする方を選びました。

## 7. 内部用は `da-` ではなく `x-` 接頭辞

`user-invocable: false` は **Claude 専用フィールドで、Cursor は無視します**。さらに **Cursor は subagent もコマンドピッカーに出します**。結果、`/da` が Claude で7件、**Cursor で12件**になっていました —— 差の5本は層別3本＋subagent 2本、どれも打つべきでないもの。

フィールドで隠す方法が両エージェントで成立しないので、**接頭辞を分けました**: `da-` は打つもの（7本）、`x-` は内部（層別3本＋subagent 2本）。どちらのエージェントでも `/da` は7件になります。

**代償**: 名前を変えると3箇所が壊れ、**3つとも無音で壊れます** —— リンタの DMI 検査スコープ、lint hook 内の同じリスト、そして **`` `x-review-<layer>` `` のようなテンプレート内プレースホルダ（名前ベースの一括置換が拾わない）**。実際に2回のリネームで2回とも取り残されました。今はリンタが検査します。

## 8. 抑制は `skillOverrides` で、`setup.sh` の管理下

**面の実数はディスク上の数の3倍以上です。** 過去2回、ファイルシステムを読んだ棚卸しがこれを外しました:

| 出所 | 場所 |
|---|---|
| ディスク上 | `~/.agents/skills/` —— 自作10、残りは上流 |
| Anthropic 管理プラグイン | `~/Library/Application Support/Claude/…`、サーバ同期 |
| **CLI バイナリにコンパイル済み** | **ファイルとして存在しない。ここが最も多い** |

**数字は書きません。** ここは以前「21 / 11 / 40 で計72」と書き、README も同じ数を書き、
`templates/claude.settings.snippet.json` は「24 / 75」と書いていて、**実測は23でした。**
同じ数を3箇所で手で維持すると3つの数になります。`/doctor` と `/skill-doctor` が実数を見ます。

description が共有する予算は**コンテキストウィンドウの1%**なので、この差は効きます。`name-only` / `off` に落としているのは（件数の出典は `templates/claude.settings.snippet.json` だけ）: `claude-api`（このリポジトリの作業で毎セッション該当するトリガ）、`anthropic-skills:schedule`（**`schedule` という名前のスキルが2本同時に生きている**）、`docx`/`pptx`/`xlsx`/`pdf`、`morning`/`setup-cowork`。

**`disableBundledSkills` は使いません。** バンドル全部がまとめて消えて実績のある `code-review`(42回) / `review`(24回) まで落ちますし、**2.1.219 にしか存在しない**ので `$PATH` の古い `claude` では黙って無効になります。

**レビュー系は意図的に抑制していません。** 4種の AI レビュアを同一146 PR に当てた計測で**指摘の 93.4% は4つのうち1つだけが検出**、4つ全部が検出したものは0件でした。効くのはレビュアの「質」より**「多様性」**です。

## 9. 横断調査は agentic search のまま、ベクトルインデックスは持たない

Milvus×Ollama のローカルベクトル DB を claude-context MCP から引く構成を検討して、採用しませんでした:

1. 上流のメンテが停滞（直近30日で3コミット）
2. **インデックスが絶対パス単位**なので、symlink で作る virtual monorepo は実体パスと別インデックスになり、二重化と鮮度不整合を起こす（公式 FAQ に明記）
3. Milvus Lite 非対応で docker 常駐（etcd＋MinIO＋Milvus）が必須。対価は自己申告の「40%トークン削減」
4. **Claude Code 自身が初期の RAG＋ベクトル DB を agentic search に置き換えています。** 作者が理由に挙げているのは security / privacy / **staleness** / reliability

代わりに virtual monorepo のディレクトリ、`rg` → `ast-grep` → LSP → 通読の段階的探索、`da-investigate` の予算、`x-codebase-explorer` の並列展開で回します。

`codegraph` は**未評価**です。評価していないものを却下したとは書きません。

## 10. 上流スキルの監査結果（2026-07-29 実施）

### 内容の監査

`skill-scanner` を全21本に実走させ、**上流11本は critical / high / medium すべて0件**。手作業でも確認:

- **`.env` / 資格情報 / base64 / `curl` / 「以前の指示を無視」の該当は全て `skill-scanner` 内**の検出パターン。それ以外の該当3件は `cp .env.example .env` と `process.env.NODE_ENV` で良性

- **不可視文字の混入0件。** Unicode Tag（U+E0000–E007F）・bidi 上書き・private use はどこにも無い。検出されたのは絵文字の異体字セレクタ（U+FE0F）と、検出器自身のパターン例の U+200B だけ

### 供給経路の監査

- **11本すべて、現在の上流 HEAD と完全一致。** 4リポジトリを clone して差分を取った結果、今 `npx skills update` を打っても変わるものは無い。つまり上の内容監査は「今日の上流」も覆っている

- スキル内容を自動生成・自動コミットする workflow はどのリポジトリにも無い

### レジストリ経由ではないこと —— ここが効いている

2026年に報告されたスキルのサプライチェーン攻撃（ClawHub 経由の30本超のマルウェア、Snyk が **ClawHub と skills.sh の3,984本**を走査して確認したマルウェア76本）は、**公開レジストリの母集団の話**です。ClawHub の公開障壁は「SKILL.md と1週間前に作った GitHub アカウント」で、署名もレビューも既定のサンドボックスもありません。

**ここはその索引を引いていません。** lock は `sourceType: github` / `sourceUrl: https://github.com/<owner>/<repo>.git` を記録していて、`npx skills add <owner>/<repo> -s <skill>` は**名指ししたリポジトリを直接 clone**します。Snyk の調査で4リポジトリはいずれも評価対象になっておらず、名前が挙がった脅威アクターは使い捨てアカウントです。

**選定規則としてこれを明文化します: 名指しした既知の保守者のリポジトリからのみ入れる。レジストリの索引から探して入れない。**

### 残る露出は3つ

1. **`npx skills` 自体が固定されていません。** これは `vercel-labs/skills`（現 v1.5.20）の npm パッケージで、**このエコシステムからこのマシンで実際に実行される唯一のコード**です（スキル本体はテキストにすぎない）。`npx` は毎回最新を取ってきてファイルシステム権限付きで走ります。**緩和策は `npx skills@1.5.20 add …` のようにバージョンを固定すること。** 現在の README は固定していません
2. **`skillFolderHash` はバージョン固定ではありません。** インストール時の記録で、ローカル改変の検出には使えますが、`update` は既定ブランチの最新を持ってきます
3. **上流11本はこのリポジトリに入っていないので CI が見ていません。** 監査したのは「このマシンの今日の中身」です

だから運用規則は: **`npx skills update` の直後に `skill-scanner` を回す。** 監査は一度で終わりません。

### 管理された例外: 自作スキルの symlink 26本が critical に出る

`scan_skill.py` は **「スキルディレクトリの外に解決する symlink」を critical** に分類します（脅威モデルは `~/.ssh/id_rsa` を参考ファイルに偽装させること）。`_shared/` への26本はこの規則に**真に該当**します。

**これは受容する例外です。** 逃げていないことを実測で確認済み（26本すべて `skills/_shared/` 配下に解決、逸脱0本）。そして `verify-skills.sh` が**リンク先を `../../_shared/<name>` に完全一致で強制**しているので、逸脱は構造的に発生しません。

**この例外を記録している理由は、コピーに戻す「修正」を防ぐためです。** それをやると、下の「`_shared/` は symlink ではなくコピーだった」に書いた4要件と検証者バイアス節が、再びどのレビュースキルにも届かなくなります。**26件の critical は、共有が実際に機能していることの裏返しです。**

## 11. 観点クラスタは実証データに突き合わせて決める（2026-07-30）

**「観点は漏れていないか」を自分の記憶で答えるのをやめた。** MSR 2022 の SmartSHARK 研究が、**マージ後に発覚した = レビューを生き延びたバグ187件**（28プロジェクト・173 PR）を分類して分布を出している。これが「何を見落とすか」の外部基準になる。

突き合わせた結果、**最大カテゴリに専用クラスタが無かった**:

| 見逃しカテゴリ | 分布 | 突き合わせ前の状態 | 対応 |
|---|---|---|---|
| **semantic**（意図と違うことをする） | **51.3%** | **クラスタ無し。** 設計妥当性と型設計はあったが「言われたことをしているか」は無かった | **クラスタ1として新設し、常時カバー対象に**（4→5本）。内訳最多の**例外処理 36.5%** を筆頭項目にした |
| build | 15.5% | クラスタ無し | **ゲートの担当**（`gate.sh verify` が実際にビルドを走らせる）。レビューで見るものではないと明示。内訳最多の build hang 58.6% は timeout が捕まえる |
| analysis checks | 9.1% | クラスタ無し | **ライセンス**を backend の依存クラスタに新設（研究の実例が「新規ファイルの license ヘッダ漏れ」）。null チェック漏れ 47.1% はクラスタ1に含む |
| compatibility | 7.5% | 名前が付いていなかった | backend のクラスタ5に**実行時互換**、frontend のクラスタ7に**プラットフォーム互換**として明示 |
| concurrency | 4.3% | 暗黙（「reliability, consistency」の中） | **クラスタ名に昇格**。「2つが同時に走ったら何が起きるか」を問う形にした |
| configuration | 4.3% | infra が部分的に | クラスタ1の「絶対値が間違っている」項目に含む（秒とミリ秒、retention 1 など） |
| memory | 1.6% | クラスタ無し | backend のクラスタ6に**資源寿命**として明示。最も捕まっていないカテゴリ |

**build と configuration を「クラスタにしない」判断が要点です。** 合わせて19.8%あるが、**これはレビューではなくゲートが捕まえるもの**で、実際にこのリポジトリは自分のゲートで `check.sh` 全ステップを走らせている。読んで気づく種類ではなく走らせて分かる種類なので、観点を増やすとファンアウトのコストだけ払って何も増えない。**分担を書いておかないと「漏れている」に見えるので明示した。**

新設したのはクラスタ1つとライセンス1つだけ。残りは既存クラスタの**名前に出した**。クラスタ = subagent 1本なので、増やすのは実コストがかかる —— 名前に出せば読まれる、という前提に乗っている。

## 12. 一枚絵は「変更」ではなく「所見の位置」を描く（2026-07-30）

レビュー報告の冒頭に **Mermaid の変更マップ**を置く。GitHub・GitLab・大半のビューアが本文内で標準描画するので、ツール不要で Claude と Cursor から同じものが出る。

**描く価値があるのは変更そのものではなく、そこに載せた所見の方です。** 差分が触った範囲の図は、ファイル一覧が既に言っている。**リスクがどこにあるかの図**は、所見一覧から読者が再構成できない唯一のもの —— 所見はファイルを名指しするので、2件が同じ辺の話だと気づくには読者が頭の中にトポロジを保持する必要がある。

規則は「素朴に作ると無い方が悪くなる」ものばかり:

- ノードは**読者が認識するもの**（画面・エンドポイント・テーブル・キュー・リソース）。**ファイルパスとクラス名は禁止** —— 内部構造の図は差分の言い換え
- **印の無い辺は「見た上で所見なし」**。凡例でそう書く。そうしないと綺麗な辺が「省略」と読める
- 載せるのは **⛔ / 🔴 / 🧭 だけ**。🟡 と 💡 を載せると重要度が「全部に印」に潰れて情報を運ばなくなる
- **マップにある所見は表にもある。** マップは索引で、唯一の掲載場所には絶対しない —— 図を飛ばした読者が何も失わないように
- **12ノード程度が上限**。それを超えると読者はリストとして走査するので、表の方が上手い
- **形が無い変更では飛ばす。** そして**飛ばしたと書く** —— 無いマップが「忘れたマップ」と読まれないように

層をまたぐレビューでは、**境界の両側が同時に現れる唯一の場所**になる。これは層別レビューが構造的に作れないもの。

## 13. 大きい差分は「レビュー」と呼ばない（2026-07-30）

**レビューは差分が大きくなると緩やかに劣化しない。** モデルは一貫性を失って**スタイルのパターン照合に落ちる** —— つまり「徹底したレビューに見えて、重要な所見を1つも含まない」出力になる。目安は1,000行。

だから読み始める**前に**測る。後から測ると言い訳と区別できない。

| 差分 | 出力は何であり、何を書かねばならないか |
|---|---|
| 約400行以下 | レビュー。全変更ファイルを通読 |
| 400〜1,000行 | レビューだが、**通読したファイルと流し読みしたファイルを名指しする** |
| 1,000行超 または 40ファイル超 | **レビューではなく標本。** 冒頭のマップの隣に明記し、標本の選び方と**一切開いていないもの**を書く |

**閾値を超えた時の正しい動きは、多くの場合「差し戻す」こと。** 大きすぎて1単位ではレビューできないと言い、自分ならどう分割するかを示す。`da-design-review` は設計時にその分割を決めているので、**未分割で到達した変更はその工程を飛ばしており、それをレビューしてしまうと飛ばした方が得になる。**

## 14. 採択率だけが「レビュアが信用されているか」の測定値（2026-07-30）

業界の信頼指標は**指摘の採択率**で、50%未満は迂回され、80%超で soft gate に載せられる水準。自動レビュアの偽陽性は一般に 5〜15%。

**このリポジトリには反証パスがあるので、偽陽性は報告に届く前に抑制されている —— が、それが効いているかを一度も測っていなかった。** そして測定値は既に生成されていた: `da-fix-plan` の **Decline 件数**がそれ。どこにも記録されていなかったので、誰も使えなかった。

`da-fix-plan` が採択率を**率として**報告し、**計画ファイルに書き込む**ようにした。1回の値は何も言わないので、蓄積が要る。

読み方は両方向:

- **50%未満 → 計画ではなくレビューを直す。** 挙げたものの半分以上が対処に値しないなら、それは雑音。
- **繰り返し100% → これも悪い兆候。** 転記しただけか、安全で自明なものしか挙げていない。

## 15. 変更内容は表で、PR 説明と同じ4列にする（2026-07-30）

レビュー報告の「変更内容」は散文の箇条書きだった。**散文だと「観測できる変化」と「実装の説明」が混ざり、混ざったものは読者が仕分ける羽目になる。** `da-pr-describe` を4列の表にした時、レビュー側は触っていなかった。

**同じ4列（領域 / 変更前 / 変更後 / なぜ）に揃えた。** 同じ変更について2つの語彙を持つと、レビューと PR 説明が食い違い、読者が突き合わせる作業を負う。

同時に、報告骨格の見出しが全部英語のままだったのを日本語にした。**「報告は日本語で書け」という指示を入れた後も骨格が英語だったので、モデルに矛盾した signal を与えていた** —— 骨格はコピーされるものなので、指示より強い。

## 16. ファンアウトは「予算」にする —— 広げるのをやめて、狭いことを正直に言う（2026-08-06）

`/da-review-all` が重い、という体感から測った。**3層の変更で subagent 約69本。** 内訳は層エージェント3本、find フェーズ29本（backend 11 + frontend 9 + infra 9 クラスタ = 1クラスタ1本）、検証6a が層ごとに最大8本、⛔/🔴 ごとに3レンズ、6b の懐疑役3本。世の中では「レビュー工程が検証者を41本呼ぼうとした」「102本」「415本」という事故報告が出ている水準で、こちらも同じ形をしていた。

**直感的な改善案（逐次の層別レビューを並列化する）は間違いだった。** 実測が逆を言っている:

- **ファンアウトは 2.6〜5.9× のトークンを使い、しかも速くならない。** 逐次 4:15 に対して2本 8:00、5本 4:45。
- **subagent は親のキャッシュ済み prefix を継承しない。** cold で立ち上がり uncached 価格を払う。3層を同時に投げれば cold な subagent 15本が同じリポジトリを同時に読み、同じファイルを最悪のレートで買い直す。

つまり**遅さと高さの原因は同じ「本数」**で、並列化はそのどちらも直さない。効く手は3つとも「本数と重複を削る」方向にある。

## コスト削減のために、ユーザが選んだモデルを黙って差し替えた（2026-08-06、同日撤回）

決定16で `x-codebase-explorer` に `model: sonnet` を固定した。理屈は通っていた —— トレースは機械的作業で、ファンアウトの大半を占め、安いモデルへの固定は実測で約37%のトークン削減。選択肢として提示して承認も取った。

**それでも間違いだった。効果を測る前に、性質を間違えている。**

`model:` を固定するというのは、**ユーザがそのセッションのために選んだモデルを、確認もログも無しに上書きする**ということです。Opus を選んだ人が Sonnet を引く。プロンプトも出ないし、トランスクリプトにも出ない。**同意していない節約は節約ではなく、ツールが黙って反対しているだけ**で、高いより悪い。

見た目より悪くしている要素が2つある:

- ~~**`model:` は Claude 専用で、Cursor は黙って無視する。**~~ **これは間違いでした。** 撤回の理由として書いたが、事実が逆です。**Cursor は subagent の `model:` を読みます**（`name` `description` `model` `readonly` `is_background`）。しかも `inherit` が Cursor 側の既定値でもある。「Claude 専用フィールドだから最適化にすぎない」という invariant 1 由来の反射が、ここでは効きません —— skill の `model:` は落ちるが、**subagent の `model:` は落ちない**。つまり固定は**両方のエージェントでユーザのモデル選択を上書き**するので、規則は緩むどころか強くなります。**撤回の結論は変わらず、根拠だけが差し替わった**ケースとして残します。
- **同じ金額は上流でもう取っていた。** ファンアウト予算が本数を29→9に落としている。**本数で取れる金を、誰かの選択を奪って取り直していた。**

**規則にした: このツールキットはモデルを固定しない。** 両エージェントの本文に理由ごと書いてあるので、次に「トレースは安いモデルでいい」と思った人がそこで止まる。コストをもう一段削るなら **subagent を「何本」動かすかで取る。「何の上で」動かすかでは取らない。**

一般化するとこう: **ユーザの明示的な選択を上書きする最適化は、効果の大小に関わらず、まず種類として不許可。** 承認を1回取ったことは免罪にならない —— 提示した時点で「セッションのモデル選択を上書きします」と言えていなかったのだから、あの承認は情報が足りていなかった。

## 「ゲートは無人運用向けではない」と宣言して、無人運用で壊れる状態機械を放置した

`README.md` には「**深夜に無人で回すためのロックではありません**」と書いてありました。今その立場は
反転しています。ただし**反転したことが学びではありません。** 学びはこちらです:

> **「対象外」と宣言することは、その経路が安全であることの代わりにならない。**
> ゲートは armed 状態を漏らし、上限なくブロックし、記録なく解放していた。そのどれも、README の
> 一文がそのケースを非対応と書いていたことによって許容可能になってはいなかった。

**位置づけはループの話でしたが、欠陥は状態機械の話でした。** 対象外と宣言したかどうかに関係なく、
以下は全部壊れていました:

| 壊れていたもの | 実際に観測されたこと |
|---|---|
| `arm` に期限が無い | 終了済みセッションの armed 状態が残り、5本のチェック（約7秒）を毎ターン走らせていた。trace.log に `passed: all gating checks green` が57回。**disarm は `da-verify` の散文に委ねられていて、散文はセッションの終了を生き延びない** |
| ブロックに上限が無い | `attempts >= 2` はメッセージを強めるだけで、内容は「`/clear` して作り直せ」—— 無人ループが取れない行動 |
| 解放が記録されない | 再入で1回だけ解放する経路が `trace` を呼んでいなかった。「何も起きなかった」と「一度も走らなかった」を区別するために作ったファイルが、**最も頻繁に起きている出来事について沈黙していた** |
| worktree に掛からない | `using-git-worktrees` はこのツールキット自身の推奨する分離手段。trace.log に `.worktrees/…  passed: armed elsewhere` が実在 |
| timeout が無い | ハーネスの timeout で殺された hook は exit 2 にならない = non-blocking。**毎ターン全テストスイートを回す profile が実在する**ので、最も現実的な fail-open 経路だった |

### そこから出た設計判断3つ

- **verdict は「存在しないもの」ではなく「存在するファイル」。** 諦めることが `ACTIVE` を消すだけなら、
  次のセッションの `status` は "not armed" と言う —— **何も arm しなかったセッションと区別がつかず、
  片方だけが「作業は未検証」を意味する。**
- **期限切れは arm からの TTL ではなく idle 基準。** arm からの TTL は可能にしたいものを殺します ——
  6時間の無人実行が飛行中に期限切れして無言で fail-open する。
- **attended / unattended のモードフラグは作らない。** 設定が必要なモードは、まさに必要なときに
  設定されていないモードで、Stop hook から人間が見ているかは確実に判定できません。挙動は一つ:
  有界で、記録され、どちらでも同一。**対話利用者にとっても退行ではありません** —— 3回失敗して
  記録を残して解放するのは、このリポジトリ自身の規則（同じ問題で2回失敗したらセッションを捨てる）を
  **印字するのをやめて実際に強制する**ことです。

そして掃除役を **cron や launchd にはしませんでした。** ガードレールを解除するのが仕事の
バックグラウンドプロセスは、誰も見ていないときに走る fail-open 機械で、しかも**他人の資格情報を含む
ファイルを編集する `setup.sh` に install/uninstall 経路を増やします。** 掃除は、全ターン終了が既に
歩いている glob の上でやります。規則は1行です: **ある呼び出しがセンチネルを退去させられるのは、
それが今まさに強制しようとしているセンチネルではない場合に限る。**

## `perl -pi` は symlink を実体ファイルに置き換える

`CLAUDE.md` は `AGENTS.md` への symlink です。一括置換で**3回壊しました**。名前ベースの sweep で直すのを諦めて、`check.sh --rewritable` が symlink を構造的に除外するようにし、`check.sh` が mode 120000 を検査します。

## zsh は `$VAR` を単語分割しない

`for s in $DEL` が文字列全体を1単語として扱い、`perl -pi ... $FILES` が改行連結されたリスト全体を1つのファイル名として渡しました。どちらも `bash -c` で包んで解決。macOS の bash は 3.2 なので `mapfile` / `readarray` / `declare -A` も使えません（`check.sh` が検査）。

## `npx skills remove` は store ディレクトリを残す

`~/.agents/skills/` に残り、**Cursor はそこをネイティブに読みます** —— Claude から削除済みに見えて Cursor では生きているスキルができます。store ディレクトリの削除まで必要。
