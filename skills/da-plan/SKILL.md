# /da-plan — 次の変更を決める

ソースや設定は変更しない。相談と依頼文の推敲は会話で返す。設計図はプレビューできる画像にし、リポジトリへの保存は仕様・図の記録を依頼された時に行う。

## 実行条件

| 条件 | 満たさない時 |
|---|---|
| 解きたい問題と求める成果が分かる | 何を決めたいか、または何を残したいかを尋ねる |
| 仕様を記録する時は対象のリポジトリと変更の内容が分かる | 足りない方を聞く。保存先の規約は仕様の手順で照合する |
| 所見の整理では元のレビューと変更の目的を特定できる | どの報告や仕様を使うか聞く。修正を始めない |

## 読むファイル

常に依頼と、利用者が対象として指定した元の資料を読む。次のうち目的に合う手順だけを開く。`${CLAUDE_SKILL_DIR}` はこのスキルのディレクトリ。変数を展開しないホストではこのファイルの親から解決する。

| 求められた成果 | その時に読むもの・進め方 |
|---|---|
| 設計の相談 | 既知の制約で決められれば推奨案と理由を返す。壁打ちを頼まれた時や、責任境界・失敗時の挙動などで人の選択が設計を変える時は、下の面談と図解へ |
| 依頼文の推敲 | 元の依頼と範囲を維持し、調べる一次資料、確かめる方法、成功の観測を具体化する。実験で決められる点と利用者が選ぶ点を分け、コピーして使える依頼文で終える |
| 仕様・実装計画の新規作成または更新 | `${CLAUDE_SKILL_DIR}/reference/spec.md`。プロファイルの `spec_system` と `${CLAUDE_SKILL_DIR}/reference/spec-system.md` から保存先・規則・検査を解決する。既存の変更を能力と対象で探す |
| レビュー報告から修正計画を作成 | `${CLAUDE_SKILL_DIR}/reference/findings.md`。所見の採否と順序を決め、修正計画の既存規約を探す。規約が無い時は `docs/fix-plans/<date>-<branch>.md`。仕様用の保存先と区別する |

## 面談と図解

1. 実装や仕様で確かめられる事実を先に調べる。面談には導入済みの `grilling` を使う。手元になくても、前提のそろった問いに選択肢・推奨・理由を添え、人の回答を待つ。回答に依存する問いは次の回へ送る。既に答えたことは聞き直さない。
2. 「誰が再試行するか」「どこに状態を持つか」のように案で境界・順序が変わる時は、内部の `x-present` に、読み手の問い・配置したい要素・根拠・合意済みの判断・未決の選択肢を渡し、PNGで見比べる。現状、提案、未決を図中でも区別する。回答で変わった箇所を描き直す。図だけの依頼なら既存資料から直接作れる。
3. 選んだ案と理由、残った問いを返す。合意したら、記録を頼まれた仕様・ADRへ引き継ぐ。並行操作や再試行の正しさが争点なら、守りたい性質・反例候補を `da-review` の設計レビューへ。再実行する検査を残す依頼は `da-write-checks` が扱う。

## 根拠の扱いと完了条件

根拠は対象の `path/file:L42` または外部の一次資料の URL で示す。観測、推奨の前提、未確認の点を区別する。書いた場合は新規か更新か、パス、検査結果を報告する。修正計画では5つのバケットの件数と判断待ちの項目、採択率を返し、実装の手前で完了する。
