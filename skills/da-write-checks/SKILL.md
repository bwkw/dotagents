# 検査を作る・育てる

成果物は、プロジェクトの次の担当者が同じ条件で再実行できる検査。検査コード・モデル・再実行手順を変更する。現行実装が約束を破る場合は、再現できた条件を報告する。依頼に製品修正も含まれる場合だけ修正に進む。

## 実行条件

| 必要なもの | 足りない時 |
|---|---|
| 守る約束を決められる仕様、利用者の要求、または既知の失敗 | 既存の判断を探し、期待が複数残るなら違いを示して聞く |
| 操作対象と検査を追加できるリポジトリ | 読めた範囲と不足を伝える。設計だけを頼まれた時は設計所見を返す |
| 既存手順の更新なら、対象の検査と実装 | 最後に対応を確認した版と現行版を比べる。実行できない範囲を記す |

## 読むファイル

常に、対象プロジェクトの規約、守る約束の出典、利用者の入口、対応する既存テストと実行コマンドを読む。順序や並行性、入力全体の性質が論点なら `${CLAUDE_SKILL_DIR}/reference/formal-methods.md` を読む。画面・CLI・サービスの実操作や手順更新なら `${CLAUDE_SKILL_DIR}/reference/operation.md` を読む。

## 手順

1. 「どの初期状態で、何をすると、利用者が何を観測できるか」を1文で決める。受け入れ条件、失敗版、期待する失敗理由を実行前に固定する。既存の検査が同じ失敗を検出できるなら、その結果を返す。
2. 例を1つ実行して判定できるなら結合テスト。値の組み合わせなら実コードへの生成入力。順序を問うなら状態探索、入力全体の規則なら実コードの検証器か定理証明を検討する。道具を選んだ理由と、選んだ方法では観測できないものを一言書く。
3. 実際の不具合、または隔離したコピーで約束を破る最小変更を使い、**同じ判定が正しい理由で落ちる**ことを確認する。欠けた依存や構文エラーで止まったものは検出に数えない。故障注入は共有中の作業ツリーやユーザーの環境に行わない。
4. 基準の実装でも動かし、両方の観測と判定を記録する。現行実装で違反を確認したら、期待値やモデルを弱めず報告する。CIへの登録や必須ゲート化は対象プロジェクトの既存規約と依頼範囲で決める。

## 根拠の扱いと完了条件

仕様と対象の `path/file:L42`、対象版、コマンド、必要な版・入力、観測、残る前提を同じ場所から辿れるようにする。プロジェクトのテスト1本で再実行できればそれで完了。複雑な実操作は、対応する機能・起動・証拠保存・片付けをプロジェクトの既存配置に残す。通常の検証実行とゲートの有効化は `/da-verify` に委ねる。
