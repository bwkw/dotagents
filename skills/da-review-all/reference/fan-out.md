# fan-out —— 大きな差分を担当ごとのレビュー役に分け、所見ごとに反証役を当てる

Step 3 で、レビュー範囲が **1,000 行を超える**時、またはユーザーが PR ごと・所見ごとの検証を頼んだ時に読む。1,000 行以下は今までどおり inline で回し、このファイルは読まない。理由と実測は `docs/decisions.md` の決定 41。

**読み取り専用は変わらない。** レビュー役も反証役も、コード・設定・作業ツリーを変更しない（ブランチを切り替えない）。

---

## なぜ分けるのか —— 独立性ではなく、抱えられる量

決定 26 が退けたのは「同じモデルの 2 つ目に独立性を期待する」ことで、それは今も正しい。ここで分ける理由は別にある。**1 つの文脈は 1 万行を全部開けない。** 開けなければ Step 1b のとおりサンプルになり、他人の積み PR では「サンプルでした」は作者の役に立たない。担当を狭めたレビュー役は、担当範囲を全部開ける。

反証役は、所見 1 件だけを持って経路を端まで追う。発見の文脈を持たないので、論証ではなく根拠だけで判断する。`verification.md` の 6a を、1 件ごとに予算を持った別の文脈で行う形である。

## 1. 担当を決める

| 単位 | いつ |
|---|---|
| **PR ごとに 1 役** | 既定。積み PR は 1 本ずつ |
| **1 PR を領域で割る** | 1 PR が生成物・check 定義などを除いて 5,000 行を超える時（例: 様式の変換と XML / BOE のタスクとデータ） |
| **突き合わせ役を 1 つ足す** | PR が 2 本以上ある時、または同じ領域を同時期に別の人が作っている時。双子の実装（同じ概念の 2 つ目の enum・ルール・ヘルパー）、マージ順で衝突する列挙、既存の兄弟との食い違いだけを見る |

担当の数は、規模の目安として 3〜8。それより多いなら分割のために差し戻す方が早い（`review-process.md` の Step 1b）。

## 2. レビュー役への依頼に必ず入れるもの

1. **対象と読み方。** PR とリポジトリ、base と head の SHA、`git -C <repo> diff <base> <head>` と `git -C <repo> show <head>:<path>`。積み PR は 1 つ下のブランチが base。
2. **担当範囲の差分ファイルを全部開く。** 生成物と check 定義は突き合わせに grep で使うだけでよい。開かなかったものは `filesNotRead` に名前で返させる。
3. **従う規律。** 層のスキル（`x-review-<layer>`）の Step 2b の適合スイープと観点クラスタ、`finding-discipline.md`、対象リポジトリの規則ファイルのパス。
4. **持ち主。** 他人の PR なら、PR 本文から意図を復元してから欠陥を探す。本文の安全主張（「値の追加のみ」「既存と同じ」）は検証対象のリストとして渡す。
5. **既に決着したもの。** 反証済み・既出の所見は名前で渡し、再提出させない。
6. **返す形。** 所見ごとに `repo`・`file`・**その PR の head での** `line`・`severity`（Must / Should / Nit / Q）・`claim`（1 文）・`scenario`（実際の値と経路）・`fix`（直し方を名前で 1 つ）。件数を絞らせない。推測は Q にさせる。

## 3. 所見ごとに反証役（`x-review-verifier`）を当てる

レビュー役が返したら、**生き残る前のすべての所見**に 1 件 1 役で `x-review-verifier` を当てる。並列でよい。依頼には所見の 4 項目と読み方を渡し、確かめることを指定する。

- その分岐が本番で走るか（呼び出し元、UI の制約、別の場所のガード、外部のチェック定義）
- 既存の兄弟が同じ形で、それが意図的か
- 比較相手の別 PR が出てくる所見なら、その PR も読む

返り値は `confirmed` / `plausible` / `refuted` と、検証後の重さと、`file:line` 付きの根拠。

**判定は所見の通し番号で紐づける。`file:line` で紐づけない。** 同じ行番号の所見が別のファイルにあると、判定が入れ違う（実際に 3 組起きた）。

## 4. 統合して Step 4 に戻る

- `refuted` は落とし、件数と 1 行の理由を 🔬 に残す。
- 2 つの役から出た同じ根本原因は、すべての `file:line` を持つ 1 件にまとめ、1 回だけ数える。
- 反証役が重さを変えたら、変えた後の重さを使う。
- ここから先（Step 4 の層またぎ、4b、5、6）はこの文脈で行う。下書きは反証を生き残ったものからだけ選ぶ。
- **投稿の直前に head を取り直す。** 動いていたら新しいコミットを読み、解消済みの所見を外し、残りのアンカーを新しい head で取り直す。

## 5. 🔎 に書くこと

「inline, no subagents」の代わりに **「fan-out: レビュー役 N（担当の一覧）、反証役 M、反証 K 件」** と書く。開かなかったファイル、自分で実行しなかったもの（typecheck、テスト、外部への送信）は fan-out でも名前で書く。所見が無い部分は「この深さでは検出されなかった」の意味であることも変わらない。

## 6. 守ること

- **モデルを固定しない。** 起動するサブエージェントはセッションのモデルを継ぐ（不変条件 10）。費用は役の**数**で抑える。
- **サブエージェントの無いホストでは inline に戻る。** Step 1b のとおりサンプルだと書き、開かなかったものを名指しし、分割を勧める。走っていない役が走ったように書かない。
- **同じ依頼を 2 回投げない。** 結果が来る前に同じ範囲を自分でも読み直すと、費用が倍になるだけ。待つ間は概要ページの骨組みなど別の作業をする。
