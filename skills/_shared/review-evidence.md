# レビュー所見の証拠

指摘は仮説として受け取り、判定・重大度・証拠の種類を別々に記録する。人数や確信度の点数は、実行結果の代わりにならない。

## 判定

| `verdict` | 必要な根拠 | 扱い |
|---|---|---|
| `supported` | 主張した範囲を裏付ける観測またはコード上の論証 | 証拠の種類と限界を添えて残す |
| `refuted` | 到達を防ぐガード、主張と矛盾する観測などの反証 | 指摘から外し、理由を1行残す |
| `inconclusive` | 実行環境・データ・仕様・追跡が不足し、どちらとも決められない | 欠陥と断定せず、何があれば決着するかを 👤 に残す |

反証を探す姿勢は維持する。裏付けを見つけられなかっただけでは `refuted` にしない。不足した情報を、問題が起きない証拠と取り違えない。変更前から同じ挙動なら今回の回帰という主張は崩れるが、既存の欠陥がない証明にはならない。

## 証拠の種類

`evidence` は配列とし、各項目に `kind`・`target`・`expected`・`observed`・`limits` を記録する。実行した項目には正確な `command` と生の出力または `artifact` の場所も付ける。

| `kind` | 確かめたもの | 限界 |
|---|---|---|
| `static` | 実コードの生成箇所・呼出経路・ガード、または明文規約との照合。`file:line` を示す | 実行再現ではない |
| `test` | 対象実装を呼ぶテストや最小再現スクリプト | スタブやfixtureが置き換えた境界を示す |
| `runtime` | 実画面・実API・対象成果物を直接観測 | 環境・入力・操作手順を示す |
| `model` | 状態遷移などを抽象化したモデルの検査 | 探索範囲と実装への対応を示す。実装の再現とは数えない |

`target` は対象の commit SHA と実装・テスト・環境を識別できる情報。CI の合成マージや、手元の依存が PR head と異なる場合もここで分ける。実行者の要約だけで判定せず、元の出力を読む。提案しただけのコマンドは `command` に入れず、`nextCheck` に置く。

振る舞いの欠陥、明文規約違反、設計上の問いは確認方法が違う。規約違反は `static` で判定できる。設計上の問いを、動作不良の再現として扱わない。実行できなくても、経路と前提をすべて示した論証で裏付けられる欠陥は `supported` / `static` とし、「コード上の裏付けあり・実行再現なし」と書く。前提が残る場合は `inconclusive`。

## 振る舞いの候補を確かめる

1. **観測を先に決める。** 入力・初期状態・操作順序と、期待する値／失敗するときの値を1つずつ定める。
2. **実コードを使う最小の検証を試す。** リポジトリの実行規約と利用可能な依存を確認し、許可された対象テスト・再現スクリプト・画面操作から選ぶ。一般論の追加レビューより先に、決着する観測を取りに行く。
3. **差分との因果を確認する。** 実行可能なら同じ検証を base/head で比べる。両方で失敗する場合は今回の回帰と断定しない。起動失敗や依存不足を製品の不具合と数えない。
4. **出力を確かめて判定する。** 原因に関係する出力を残す。fan-out の親は、安全に再実行できる検証を再実行し、それ以外は出力を直接確認して再実行しなかった理由を書く。

再現のために欠陥をコードへ書き直さない。価格計算なら対象の関数を import し、競合なら実際のハンドラやRepositoryを通す。競合順序は待合せや同期点で制御し、偶然の sleep だけを再現の根拠にしない。

ソースと設定は変更しない。検証コード・出力が必要なら、分離した一時ディレクトリを使う。テストがDB等を書き換える場合は、許可された使い捨て環境に限定する。秘密情報や本番状態を必要とする検証、依存の追加、デプロイ、migration、禁止された全件チェックへ自動で範囲を広げない。

**読み取り専用の反証役は権限を広げない。** 実行が必要なら、対象・正確なコマンド・期待する観測を `nextCheck` として親に返す。親は自身の権限と上の条件を確かめて実行し、出力を返す。実行できない理由を記録して静的な判定を続ける。利用可能な検証まで人間へ丸投げしない。

## 再利用と追加確認

再実行できるコマンド、入力、期待値、出力をレビュー成果物に残す。回帰テストを製品リポジトリへ追加するのは実装修正の担当へ渡し、レビューだけの依頼では変更しない。

「他にもないか」と聞かれたら、既に読んだ差分を漫然と回し直さず、未検証の境界を操作にする。例: キャンセル→再受付→旧結果の到着、編集中の言語変更、様式の適用開始日前日。共有の正本や明文規約の確認も維持する。単純な検証で決まらない並行性・状態遷移に限りモデル検査を検討し、モデルの反例を実装へ戻して確かめる。

新しい観測や追跡先がなくなったら、同じ主張の討論を増やさず、残る限界を報告する。
