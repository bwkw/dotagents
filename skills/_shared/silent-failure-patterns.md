# 静かで不可逆な失敗のパターン

**発見フェーズと検証フェーズの両方で読む。** 差分では綺麗に見え、本番で静かな障害になるパターン。どれも 1 つの観点クラスタに属さない横断的なもので、それぞれ、他は丁寧だったレビューが見落としてきた。

当てはまるなら、**原因が差分の外にあっても挙げる。** 差分は探し始めた場所であって、報告してよい範囲の境界ではない。

---

## 1. グローバルなデフォルト × 局所的な補正

変更が **共有されたもの** — タスクやジョブのカタログ、基底クラス、共通設定、DB のデフォルト、seed — に振る舞いを足し、その正しさが **呼び出し元の補正** に依存する: コンテキスト値の埋め込み、フラグの設定、前処理の実行。

失敗の形: PR の 1 経路は正しく補正している。残りの 4 経路はしていない。

具体的にやること:

1. 同じ集約やパターンを呼び出し・変更できる **すべての** 経路を `grep` する — 他のコントローラ、ユースケース、バッチジョブ、イベントハンドラ、管理ツール、本番経路の代わりをするテスト。**経路だけでなく、同じ不変条件が適用されるべき面も数える** — 兄弟のレスポンスフィールド、別の書き込み入口、非 HTTP の経路。1 つだけが丁寧にガードされ、隣が素通りする形を疑う。
2. それぞれを補正と 1 つずつ照らす。PR が触った経路で止めない。
3. 次に、何が不変条件を *強制* しているかを問う。新しい呼び出し元が忘れた時に失敗するガード、DB 制約、アーキテクチャテストはあるか。**何も無ければそれが所見** → **🧭**、実害への経路が読めるなら **🔴**。

飛ばされるのは最後の手順。「今の呼び出し元はたまたま全部正しい」はスナップショットであって不変条件ではない。5 番目の呼び出し元は、この PR を読んでいない人が書く。

**呼び出し元を列挙したコメントが兆候。** 「この 3 経路からのみ取得」「必ずロック取得後に呼ばれる」— 不変条件を、何も検査できない唯一の場所に書いたもので、具体的に数えてあるせいで保証に見える。書いた日には真で、4 つ目の入口が現れた日に黙って偽になる（その入口の作者は、何にも誘導されないのでコメントを開かない）。代わりに仕組みを求める: 新しい呼び出し元が迂回できない **チョークポイント**（操作を始められる唯一の関数の中でロックを取る）か、集合の外に呼び出し元が現れたら失敗するアーキテクチャテスト。**doc コメントは意図を記録するだけで、決して強制しない。**

## 2. fail open か fail closed か — 沈黙はどちらに倒れるか

すべてのデフォルト値、評価エラー、コンテキストの欠落、キーの欠落について、**フォールバックの向き** を確定させる。

不可逆・法的義務・外部から見える・課金される操作が、**黙ってスキップ・自動完了・no-op** の側に倒れるなら、その向きが正しいかを問う。たいてい正しくない。

> **黙って失敗するのは、うるさく失敗するより害が大きい** — 目に見える過剰実行より大きいことも多い。うるさい失敗はその日のうちに直る。黙ったスキップは監査人・顧客・規制当局が見つける。

欠けた分岐だけでなく、向きそのものを所見として挙げる。→ **🧭 / 🔴**

### 暗黙のフォールバックは、それ自体が所見

**値が無い時に、コードが黙って何かを決めて先へ進む形は、向きを確かめる前に所見にする。** 問いは「このフォールバックは安全か」ではなく、**「不在（バグ・設定漏れ・コンテキスト未設定）と、正規の値（空・0・無期限・既定）が、同じ値に潰れていないか」**。潰れていれば、壊れていることが誰にも見えなくなる。直し方は既定で **fail closed**: 型で required にする、境界でパースして落とす、環境変数は起動時に `getOrThrow` で落とす。

差分の中で次の形を見つけたら、1 つずつ「何と何が潰れるか」を言う。

| 形 | 潰れるもの |
|---|---|
| `?? 既定値` / `\|\| ''` / `\|\| 0` / `?? []` | 「渡し忘れ」と「本当に空・0」。`\|\|` は `0`・`''`・`false` という正規の値まで既定値に置き換える |
| optional な引数・フィールド（`x?: T`）で、省略すると権限・範囲・寿命が**広がる**もの | 「指定し忘れ」と「無制限」。`sessionPolicy?:` を省略すると親ロールの全権、`durationSeconds ?? 3600` は上限の消失 |
| `null` を「無い」と「無期限・全部・該当なし」の両方に使う | `expiresAt: null` が「期限なし」なのか「読めなかった」なのか |
| ORM・クエリの条件に `undefined` が入りうる | 条件ごと消えて全件対象（Prisma の `where`）。テナント列なら越境 |
| オブジェクトの組み立てで `undefined` を素通りさせる | `{ ...base, x: input.x }` の `undefined` が既存の値を上書きする / `JSON.stringify` がキーごと落とす / 更新 API に `undefined` を渡すと「変更なし」になり、意図した消去が起きない |
| `?.` の結果をそのまま真偽値や数値に使う | `if (user?.isAdmin)` の「読めなかった」と「false」、`Number(x?.count)` の `NaN` が比較で常に偽になる |
| `catch` してログだけ出し、続行する / 既定値を返す | 「失敗した」と「結果が空だった」。監査・記録・通知の失敗を握りつぶして本処理を続ける形は特に |
| sentinel 文字列（`'unknown'`、`'lacked-env'`、`'default'`）で欠落を表す | sentinel と本物の値が同じ型で流れ、等値比較を忘れた経路で本物として使われる |
| 黙った切り詰め・丸め・サニタイズ | 制限を超えた入力と、正しい入力。超えたなら止める |
| スキーマの `.optional()` / `.default()`、`exactOptionalPropertyTypes` 無効での `?:` | 「送られなかった」と「既定を選んだ」。契約に置いた既定値は、全クライアントの省略を黙って受け入れる |
| `switch` / マップ引きの `default:` 分岐で既定の扱いをする | 新しく足した種類が、既定の扱いで黙って通る。`never` での網羅（`satisfies Record<…>`、ts-pattern の `.exhaustive()`）にする |

**重大度**: 潰れた先が**許可・無制限・続行・全件・別テナント**なら 🔴（到達経路を示せる時）。それ以外も、具体的に何が潰れるかを言えれば 🟡 で、確信度 80 の閾値で落とさない。「値が来ないことは無い」は主張であって、型・パース・制約・起動時の検査のどれかが**強制していることを `file:line` で示せた時だけ**クリアにする。

**`??` を見たら、右辺ではなく左辺を見る。** 左辺が `undefined` になる経路はどこか、それはバグか正規の状態か。バグなら既定値ではなく型か例外で止める。正規の状態なら、その状態に名前（判別共用体の変種、明示的な `'UNLIMITED'` など）を付けて、不在と区別できる形にする。

## 3. 一度 SSOT と宣言し、二度ハードコードする

1 か所 — 設計文書、ドメイン定数、enum — で正と宣言された対応表・定数・対応関係が、**別の場所で再びハードコードされる**: seed、別の層、別の入口、テストフィクスチャ、インフラのテンプレート。

2 つを突き合わせている場所を探す。**比較するテストが無ければずれ、そのずれは静か。** 報告する。→ **🟡**

見つけるのは安いのに、ほとんど探されない。識別子ではなくリテラル値で検索する。

## 4. 実行時に読む seed と設定、デプロイ順序との衝突

seed・カタログ・設定が **起動時にスナップショットされず、アクセスのたびに読まれる** なら、変更はロールアウトの窓を開く: 一部のインスタンスで古いコードが動いている間に、新しいデータが有効になる。

次の 3 つを確定させる。

- **いつ** 変更が効くか — マージ時に自動、デプロイ時、手作業の手順。
- アプリのロールアウトに **対して** — 前か、途中か、後か。
- 厳格な順序のゲートがあるか、それとも安全な順序は誰かが覚えているだけの慣習か。

実行タイミングをリポジトリから確定できなければ、それは綺麗な通過ではなく 👤（人間の判断が必要）。デプロイ順序は、書いた人には自明で他の全員には見えないものの典型。

## 5. 静かな成功の可観測性

不可逆な操作が **条件付きでスキップ・自動完了されうる** なら、その後にどんなシグナルが残るかを問う。テーブルの行は受動的な証拠で、誰かが見ようと思った時にしか状態を伝えない。スキップを検出可能にするのは **能動的なシグナル** — ログ行、メトリクス、アラート。

無ければ失敗は検出できず、それが所見。→ **🟡**

> **常駐のスイープや cron ジョブを安易に修正案にしない。** 検出の穴を、独自の失敗の仕方を持つ常時稼働のコンポーネントと交換することになる。受動的な監視 1 つと、文書化された手動の復旧を優先する。常設の仕組みは、復旧が本当に人間を待てない時だけ提案する。

## 6. 検査したつもりの検査 — 発動条件を、守ると称する条件と突き合わせる

ガード・フォールバック・網羅チェック・「検査つき」と書かれた文書を見たら、**それが実際に発動する条件**を書き出し、**それが守ると称する条件**と重ねる。2 つはめったに一致せず、**ずれた側は静か**である。パターン 2 が沈黙の *向き* を問うのに対し、これは防御が **そもそも発動するか** を問う。向きが正しくても、発動しなければ守っていない。

3 つの現れ方。どれも差分では防御的で丁寧に見える。

- **補集合が素通りする。** `a ?? fallback(x)` は `a` が null のときしか守らない。`a` が不正値・空文字・古い値なら素通りする。説明が「空欄なら X」と言い、実装が「既存値が無ければ X」なら、**既存値があるときの挙動は誰も書いていない**。説明と実装のどちらが正かを作者に決めさせる。
- **宣言だけの検査は何も落とさない。** 型で網羅を主張しても、**値として消費されなければコンパイルは通る**（`type _Cov = [A extends B ? true : never]` は `[true, never]` という正当な型である）。`const _c: _Cov = [true, true]` にして初めて never 側が落ちる。結果を捨てる assert、どこからも呼ばれないバリデータ、条件が常に偽のテストも同じ形。
- **文書が主張する検査。** 設計文書・spec・コメントに「検査つき」「担保」「保証」が現れたら、対応する実装を `grep` する。無ければ文書が嘘。**別の場所に在れば、そこが発動条件の隙間**（境界の外側、ガードより前に走る副作用）。読んで納得で止めず、違反入力を 1 つ通して落ちることまで確かめる。

やること: 発動条件を 1 文で書き、**その否定で同じ障害が起きるか**を問う。起きるなら、防御が無い場合と同じ重さで報告する。「守られているケースがある」は「守られている」ではない。→ **🟡 / 🔴**（不可逆な操作の手前なら 🔴）

## 適用の仕方

クラスタを横断して 1 回、両フェーズで。

| フェーズ | このファイルの用途 |
|---|---|
| **発見** | 割り当てられた観点に *加えて* 回すチェックリスト。担当クラスタが「テスト」でも、読んでいるものにパターン 1 は当てはまる。 |
| **検証** | 発見フェーズが見落としたものを探す場所。綺麗なクラスタ報告は主張であり、その主張がたいてい外れるのがこの 6 つ。 |

ここからの所見も他と同じ規律に従う — [`finding-discipline.md`](finding-discipline.md) を参照。既知のパターンだからといって、追跡した経路と確信度スコアが要らなくなるわけではない。
