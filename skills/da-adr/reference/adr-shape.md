# ADR の型 —— 判断の記録として書く

`final-design.md` が「誰に向けて書くか」を決め、このファイルが「どういう形で書くか」を決める。
**見出し・番号・配置はリポジトリの既存 ADR に合わせる。** 以下の内容を既存の節へ組み込み、判断の適用範囲や根拠の時点まで省略しない。

ADR は決定の羅列ではない。**「なぜこうなっているのか」と聞いた新規参加者が、読んで自分で判断できる**
ための記録である。結論を引き継げる条件と、条件が変わったときに確かめ直す箇所を残す。規範（何をすべきか）はコードとスキーマコメントにあり、ADR は判断（なぜそれを選び、
何を諦めたか）を持つ。

---

## 構成

上から順に置く。**★は必須**。それ以外は判断の性質に応じて置き、置かないなら理由がある。

| 節 | 中身 |
|---|---|
| ★ `# ADR: <結論を 1 文で>` | タイトルが結論そのもの。「〜は〜で表し、〜する」。トピック名（「〜の設計」）にしない |
| ★ `## 状態` | 「採用。」＋対象範囲（何を扱い、何を扱わないか）。隣の ADR やスキーマコメントが正典の部分は、そちらへリンクして「本 ADR は〜を選ぶ理由を扱う」と線を引く |
| ★ `## この ADR が答える問い` | 番号付き。各問いの末尾に `（§N）`。読み手が実際に口にする形の問いにする |
| ★ `## 先に結論の要約` | 箇条書き。**問いと 1 対 1**、各行末に `（§N）`。ここだけ読めば判断が分かる |
| `---` | 要約と本文の区切り |
| `## 0. 前提` | 判断時点の事実・用語・現状と出どころ。守るべき条件、優先したこと、前提にした仮定や見込みを区別し、結論がどの範囲で使えるかを示す |
| ★ `## 1.` 〜 `## N.` 判断 | 見出しは**主張文**（「承認プロセスを置かない」「集約境界は利用者単位」）。1 節 1 判断。本文は「何をするか → なぜか」。比べた案は、その節の末尾の `### N-k. 却下した代替案` に置く（下の「却下した代替案」） |
| `## 却下した代替案` | **判断をまたぐ案だけ**を置く例外の節。どの案も 1 つの判断に属するなら作らない |
| `## 失っているもの（評価つき）` | 選んだ形で**できなくなること**を、影響の大きさの評価つきで。どれが最も効くかの順位も書く |
| `## 想定される疑問` | 見出しを `### 「〜ではないか」` と読み手の声で書き、答える |
| `## いつ考え直すか` | 引き金、先に確かめること、比較し直す選択肢と、変化を確認する担当・機会。未定の担当や方法は未定と残す。引き金から次の方式を自動的に決めない |
| `## 実装と前提の確認` | 判断が実装されているか、期待した結果が出ているか、前提が今も成立するかを分ける。後日の確認には日付・対象・方法・限界を付ける |
| `## 関連ドキュメント` | spec、隣接 ADR、外部の正典 |

### 判断の節の中に置くサブ見出し

必要に応じて `###` で添える。

- **上限** —— `### 上限: 〜` として、この判断が成り立たなくなる条件や、集約に載りうる例外を独立に書く
- **命名** —— 名前が一般的な語と違う意味で使われているなら、その理由を書く。同じ語を 2 つの問いに名乗らせない
- **読んでよい場面** —— 判断の例外が正しく使われる場面を列挙する
- **却下した代替案** —— 節の最後のサブ見出しとして `### N-k. 却下した代替案` を置き、案は `#### 案 N-a: 〜` で並べる。書き方は次の節

## 却下した代替案

比べた案は、それを退けた判断の節の末尾に置く。読み手は「なぜこうしたか」と「何と比べたか」を同じ場所で読め、案の「勝つ条件」と同じ節の「上限」を並べて見られる。
末尾の独立節に集めると、読み手は判断ごとに末尾まで飛んで案を拾い集めることになる。

- **置き場所**: 1 つの判断に属する案は、その節の `### N-k. 却下した代替案` に置く。`k` は既存のサブ見出しの次の番号にし、既存の `§N-m` を振り直さない。判断をまたぐ案だけを、例外として独立の `## 却下した代替案` に置く
- **記号**: 節ごとに `案 N-a`、`案 N-b` と出現順に振る。節の中の特定のサブ節に向けた案は、見出しの末尾に `（§N-m）` を付ける
- **中身は 3 点**を、この順に箇条書きで書く
  - **手に入るもの** —— その案を採れば得られるもの。案が魅力的な理由を先に公平に認める。認められない案は、真剣に比べた案ではない
  - **採らなかった理由** —— **あるべき設計として、なぜその案が正しくないか**を、問題の性質（出来事の持ち主、正本の数、失敗の単位、依存の向き、寿命の違いなど）から書く。その案を採ると何が起きるかまで書き、「〜を優先した」「今は要求が無い」で止めない
    - 同じ change の spec・design・計画の決定を理由にしない。それらは ADR の判断から導かれた成果物なので、引くと理由が循環する。「design.md の D9 でこう決めた」は理由ではなく、判断の言い換えである
    - 事実は、コード（`path:L42`）・実測・一次情報で示す。調査記録は一次情報への道案内として引いてよいが、理由そのものは本文で言い切る。出典の無い量は書かず、測っていなければ未測定と書く
  - **勝つ条件** —— 何が変われば、この案が選び直されるか。同じ節の「上限」や「いつ考え直すか」の項目に当たるなら、その名前を引いて対応させる。当たる項目が無いなら、その条件を `いつ考え直すか` に足すかを検討する
- 判断の節自体が「X を置かない」形で却下を内包していても、比べた案の 3 点が節の本文に無いなら、却下した代替案として書く

## 書き方

1. **読んで動ける言葉で書く。** 制約は「表現できない」で止めず、**何ができず、何は答えられるか**まで書く。
   ✗「履歴が交差するケースは表現できない」 ✓「答えられないのは再登録の回数と、どの登録が失効したかである。その日に有効かどうかは答えられる」
2. **将来の変更は、選び直すための材料を書く。** 引き金が起きたら、要件・実測・運用条件の何を確かめ、どの案を比較するかを書く。
   変更する箇所や移行の要否を示す場合は、確認した対象と範囲を添える。将来も同じ箇所数で済むと断定しない
3. **見出しが誤りを前提にしない。** ✗「分け方を誤っても戻せる」 ✓「分け方は、既存のデータを書き換えずに変えられる」。
   性質として述べる
4. **測っていないことを「小さい」「低い」と言い換えない。** 評価には根拠（件数・証言・一次情報）を添えるか、未測定と書く
5. **外部出典は論拠に使う箇所へインラインで貼る。** 末尾の参考文献に寄せない
6. **表は N×M の対応にだけ使う**（「答えるもの × 書き手」など）。1 次元の列挙は箇条書き
7. **太字は「ここだけは通したい 1 文」に絞る。** 句読点の直後に `**` を置かない（`SKILL.md` Step 5）
8. **記号は順に振る。** 却下案が「案 5-c → 案 5-a」のように並ぶと、後から差し込んだ跡が見える。書き直すたびに節の中で振り直す

## 前提と確認の書き分け

- **守るべき条件**は、方式を選び直しても満たす必要がある業務・契約上の条件。業務条件だけから特定の実装方式が必然だと書かない。
- **優先したこと**は、複数の条件を満たす案のうち、今回どれを重く見たか。優先度が変われば他の案も選べる。
- **前提にした仮定や見込み**は、方式の比較に使った想定。採用時に確かめた事実と未確認の仮定を分け、外れた場合に影響する判断を残す。将来の処理量の見込みは、現在の負荷での測定だけでは確定しない。判断が決まっていない不足情報は質問する。

実装上の事実、結果の計測、前提の継続確認は別の証拠である。テストの存在から本番の性能や運用条件の成立まで言い切らない。
後日の計測は後日の確認として追記し、当時それを知って選んだように理由を書き換えない。
コードから推定した理由は調査の仮説であり、当時の判断者の根拠として補作しない。

## 再検討の引き継ぎ

見直す条件が書いてあっても、その変化を誰も確認しなければ、結論は使われ続ける。
計測や要件の確認で変化を把握するなら、どの役割が何を、どの機会に確認し、再検討を始めるかを記す。
たとえば同期方式を待ち時間の超過で見直すなら、測定条件や負荷を比較するだけでなく、その計測を確認する役割と、超過時に設計を検討する役割を引き継ぐ。
既存の運用やレビュー手順が担うなら、その参照でよい。担当や確認方法が決まっていなければ未定と書き、合意済みの仕事として補作しない。

## 既存 ADR を更新するとき

- **コードから参照されている §番号・見出しアンカーを壊さない。** 更新前に ADR のファイル名と `§` で参照を検索する。
  番号を変えるには参照側の更新も必要になる。ADR だけを編集する依頼なら番号を維持する。
- 説明を整えるときは、会話の順序を外して読み直せる形にする。ただし、当時の判断と根拠の時点を保つ。
- 判断を選び直すときは、以前の判断・適用範囲・根拠を残し、何を、なぜ、いつ置き換えたかと新旧の関係を明示する。
  新しい ADR に分けるか同じファイルに残すかは、リポジトリの規則に従う。以前に採用した案を、当時から却下していた案に書き換えない。

## 書き終えたら

- [ ] タイトルだけで結論が分かる
- [ ] 問い・要約・本文の §番号が 1 対 1 で揃っている
- [ ] 前提の事実に出どころがある
- [ ] 却下した代替案が、それを退けた判断の節の末尾にある（独立節は判断をまたぐ案だけ）
- [ ] 各案に「手に入るもの」「採らなかった理由」「勝つ条件」があり、理由の数値に出典か「未測定」がある
- [ ] 採らなかった理由が、あるべき設計の議論として立っている。同じ change の spec・design の決定を根拠にしていない
- [ ] 「何ができなくなるか」が、読んだ人が判断できる具体さで書かれている
- [ ] 評価の語（小さい・十分・低い）すべてに根拠か「未測定」がある
- [ ] 条件・優先事項・仮定や見込みが区別され、採用時に未確認だったものと、後続の人が確かめる範囲が分かる
- [ ] 再検討の引き金が次の方式を決めつけず、確認事項と比較する案につながる。確認する担当・機会が分かり、未定のものは明記した
- [ ] 判断時点の根拠と後日の確認が分かれ、置き換えた判断をたどれる
