# 依頼から動く変更まで

## 実行条件

| 条件 | 足りない時 |
|---|---|
| 求める振る舞いと変更対象を特定できる | 仕様・既存例を読んで、結果を変える未決事項だけ尋ねる |
| 変更または修正を依頼されている | 原因だけなら調査、選択肢なら計画、所見ならレビューに留める |

## 読むファイル

常に対象リポジトリの規約、依頼の受け入れ条件、利用経路、そこを通る既存テストを読む。計画が渡された時は該当箇所、障害なら失敗の入力・ログ、作業途中なら差分と既存の作業記録から始める。

## 手順

1. 依頼を、利用者の入口から観測できる完了条件にする。失敗時の挙動・既存利用者の互換性も含める。元の期待を保存してから作業を始める。
2. 不具合なら `/systematic-debugging` の手順で同じ入力から原因を絞る。新機能も修正も `/test-driven-development` に沿い、実装前に意図した理由で落ちるテストを確認する。できる限り本物の境界を通す。
3. 受け入れ条件を満たす最小の変更を作る。合意済みの計画があれば `/executing-plans` の節目を使う。独立した作業を分ける時は所有範囲と統合後の確認先を決める。小さい変更はその場で完結する。
4. 同じ入口で失敗から成功への変化を確かめ、周辺の既存チェックに戻す。プロファイルがある場合、作業中のゲートと完了時の検証は `/da-verify` の規約に従う。承認された反復実行にはプロジェクトの既存ループを使う。

## 根拠の扱いと完了条件

変更した箇所、先に観測した失敗、変更後のコマンドと実測を対応付ける。対象外の環境、実行できなかったテスト、残る判断を明記する。仕様の期待と実装が矛盾したら、期待値を都合よく書き換えずに根拠を示す。コミット、PR更新、公開は依頼の範囲に従う。
