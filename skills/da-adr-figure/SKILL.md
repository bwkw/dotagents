# /da-adr-figure — ADR の要点だけを、ひと目で分かる 1 枚にする

図解 1 枚につき**定義 1 ファイル**（`figure.json`）を書き、`${CLAUDE_SKILL_DIR}/scripts/figure.mjs` で PNG にする。
図は ADR の写しではなく、要点の整理である。**図を見た人が、最初の要約で何を決めたかを知り、カードで「何を選び、なぜか」を掴める**ことを目指す。
全部の判断・全部の理由・全部の対抗案は載せない。載せると要点が埋もれる。残りは ADR に任せ、図からは ADR へ案内する。

触ってよいもの: 作業ディレクトリ（scratchpad を推奨）に置く定義・HTML・PNG だけ。**ADR は書き換えない。** 図に書きたい理由が ADR に無ければ、止まって報告する（Step 4）。

## 実行条件

1 行でも満たさなければ即座に止まり、どの条件かを報告する。続けない。

| 条件 | 満たさない場合 |
|---|---|
| 図にする ADR のファイルかページが特定できる | 聞く。会話の記憶から ADR の中身を補わない |
| 書き出し（`build`）をするなら依存が入っている | `node ${CLAUDE_SKILL_DIR}/scripts/figure.mjs setup` を案内し、入れてよいか聞く。定義を書いて `check` するまでは依存なしで進めてよい |
| 図に載せてはいけないもの（顧客名・実在の人名・社外秘の数値）を確かめてある | 聞く |

## ワークフロー上の位置

| 上流 | このスキル | 下流 |
|---|---|---|
| `/da-adr`（ADR を書いた・直した後に、Step 6 から呼ばれる） | `/da-adr-figure` | 図を ADR の要約の先頭に置く。図で ADR の弱い所が見えたら `/da-adr` に戻る |

## 読むファイル

### 常に読む

| ファイル | 理由 |
|---|---|
| 図にする ADR の全文 | 要約とカードの中身はすべてここから取る |
| `${CLAUDE_SKILL_DIR}/reference/figure-format.md` | 要約とカードの書き方の規則と、定義（JSON）の形 |

### 条件つきで読む

| ファイル | 条件 |
|---|---|
| ADR が引いているコード・スキーマ | カードに識別子（キュー名・テーブル名）や数値を載せる時。存在と値を確かめる |
| `${CLAUDE_SKILL_DIR}/reference/example.json` | 定義を初めて書く時の見本 |

> 「念のため」全部を読むことは禁止。

## 手順

### Step 1. 要約を書く

ADR の結論を、ADR を読んでいない人向けに **1〜3 行**（各 80 字まで）で書く（`summary`）。図の一番上に置く。
1 行目は「何を決めたか」で、図では結論として大きく強調される。2 行目以降は、読み手の動きが変わること（使い方・運用・制約）で、補足として控えめに描かれる。背景・経緯・検討の過程は書かない。

### Step 2. 全体像を描くか決める

ADR の判断がデータや処理の流れ（どこで何を作り、どの順で渡すか）に関わるなら、**全体像（`overview`）を置く**。流れは文より図の方が速く伝わる。
2〜4 段で左から右へ描き、箱の名前は ADR と同じにする。段の下の注記（`note`）に、その段の決まりを一言で書く（「全種類が揃うまで待つ」など）。
流れに関わらない判断（権限・命名・運用の決まりだけ）なら、全体像は置かない。

### Step 3. 要点を選ぶ

ADR の判断の節から、**読み手の動きや理解を変えるものを 4 つまで**選び、1 つをカード 1 枚にする。順は ADR の節の順にする。
**全体像で見える判断（どこで作るか・どの順か）はカードにしない。** 全体像とカードで同じことを描くと二重になり、流れに出ない判断（照合・運用の制約など）が埋もれる。全体像を置いたら、カードは流れの図に出ない判断だけにする。
**カードにするのは ADR の判断（結論の節）だけ。** 「選んだことで失うもの」や有効にする手順のような帰結・運用手順は、決定ではないのでカードにしない。読み手に要るなら、関わる判断のカードの「限界」に置く。
選ぶ基準は「これを知らないと誤解する・誤った使い方をする」か。実装の細部、当然の判断、要約に書いたことの言い直しは選ばない。
選ばなかった判断は、報告にその見出しだけを並べる（図には載せない）。全体像に吸収した判断は、そう書く。

### Step 4. カードの中身を書く

`figure-format.md` の「カードの書き方」に従う。要点:

- **決定**: 何をするかを、具体例か実際の名前で 1 文
- **なぜ**: 一番強い理由を 1 つ。「〜が違うため」で止めず、仕組み（何をすると、どこで困るか）まで
- **ボツ案**: 読み手が真っ先に思いつく対抗案が 1 つあるときだけ、「その案だと何が起きるか」と一緒に置く。無ければ置かない
- **量の上限**: カード 4 枚、見出し 40 字、決定 70 字、なぜ 1 つ（70 字）、ボツ案 1 件、表は 1 つで 3 行まで。上限は `check` が検査する。超えたら削る

**ADR より強い理由を図に書かない。** 書きたい理由が ADR に無い、または ADR の理由が弱くて図だけを読んだ人が反論できる時は、図を作る前に止まり、ADR のどこに何が足りないかを報告する。図と ADR の理由がずれると、読み手は弱い方の文書を信じる。

### Step 5. 定義を書いて検査する

```bash
node ${CLAUDE_SKILL_DIR}/scripts/figure.mjs check figure.json
```

要約の無い図、5 枚以上のカード、`決定` と `なぜ` の無いカード、`result` の無いボツ案、列の数が合わない表、量の上限を超えた文は、書き出す前にここで落ちる。上限は `scripts/figure.mjs` の `LIMIT` にある。**上限を上げて通さない。**

### Step 6. 書き出して、目で確かめる

```bash
node ${CLAUDE_SKILL_DIR}/scripts/figure.mjs build figure.json figure.png
```

文字が枠からあふれると、確認用の PNG を書いたうえで失敗し、あふれた箇所を挙げる。文言を詰めて書き出し直す。**枠を小さくしたり、あふれを隠したりして通さない。**
通ったら PNG を開き、「要約の 1 行目だけで何を決めたか分かるか」「全体像だけで流れが追えるか」「カードごとに最初の 5 秒で決定と理由が目に入るか」を確かめる。入らなければ Step 1〜4 に戻って削る。

## 根拠の扱い

- 要約とカードの理由・数値・識別子は、ADR か、ADR が引くコード・実測にあるものだけを書く。
- 場所を示すときは `path/to/file.ts:L42` の形で示す。
- 確かめられなかった数値は図に載せず、「確認できなかった」と報告する。
- 事実と推論を分ける。図に推論を書くなら、ADR に同じ推論があることを確かめる。

## 出力

作業ディレクトリに `figure.json`・`figure.html`・`figure.png` の 3 つ。報告には PNG のパス、図に載せなかった判断の見出し、ADR に足りなかったもの（Step 4 で止まった時）を書く。

## 完了条件

- [ ] 先頭に要約が 1〜3 行あり、それだけで何を決めたか分かる
- [ ] 流れに関わる ADR には全体像があり、全体像で見える判断をカードで繰り返していない
- [ ] カードは 4 枚以内で、読み手の動きや理解を変える判断だけを ADR の順に並べた
- [ ] カードはすべて ADR の判断で、帰結や運用手順をカードにしていない
- [ ] すべてのカードに「決定」と一番強い「なぜ」が 1 つあり、なぜが仕組みまで書かれている
- [ ] 図の理由・数値・名前が ADR と一致し、ADR より強い理由を図だけに書いていない
- [ ] `check` が量の上限込みで通り、全体像とカードで同じ内容を描いていない
- [ ] `build` があふれなしで通り、PNG を目で確かめた
- [ ] 図に載せなかった判断の見出しを報告した

## 次に

図は ADR の「先に結論の要約」の先頭に置き、要約の箇条は消さずに図の下に残す（図に載らない判断も箇条で見える）。図で ADR の弱い所が見えたら `/da-adr` で ADR を直し、図を書き出し直す。
