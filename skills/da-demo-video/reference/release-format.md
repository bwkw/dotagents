# セールスとCS向けリリース共有の型

## 短編と詳細の役割

共有会の短編は75〜90秒を目安に、最大120秒で作る。
1本で伝える中心価値は1つ、デモも1点に絞る。
見終わった人が、その価値を必要とする顧客と、提案する場面を思い浮かべられる構成にする。

初期設定、全操作、例外対応、技術仕様は非同期の詳細共有へ回す。
長編動画を別途依頼されたら短編と別に作り、NotionやPRなど既存資料で足りる場合はそこへ誘導する。
詳しい資料がまだなければ、架空のリンクを置かず、共有本文に作成予定と書く。

## 冒頭の1枚

最初のフレームから、価値を表す短い見出しと次の3行を同時に見せる。
ロゴだけのオープニングや別のタイトルカードは挟まない。

| ラベル | 表示本文の上限 | 内容 |
|---|---|---|
| 誰の | 20字 | 価値を受ける具体的な役割や担当者 |
| どの業務 | 30字 | 困りごとが生じるフローや利用場面 |
| どんな価値 | 30字 | 省ける作業や解消する困りごと |

例（架空のリリースを想定した表現例で、実機能の主張ではない）:

```text
入社準備の確認先をひとつに

誰の　　　　入社準備を担う人事担当者
どの業務　　入社前の手続き状況の確認
どんな価値　確認先をまとめ、確認の手間を減らす
```

「一覧機能を追加」は機能の説明なので、価値の欄にはその結果省ける作業を書く。
「生産性向上」だけでは変化が分からないため、何の手間が変わるかまで具体化する。
値の長さはラベルを除き、句読点や空白を含めて数える。
冒頭のナレーションは3行を自然な1〜2文にまとめる。

## 90秒版の時間配分

| 時間の目安 | 画面 | 伝えること |
|---|---|---|
| 0〜15秒 | 冒頭サマリ1枚 | 誰の、どの業務に、どんな価値があるか |
| 15〜30秒 | 困りごとが分かる実画面または簡潔な比較 | 従来の困りごと1つと、今回の変化 |
| 30〜60秒 | 主要デモ1点 | 業務場面、必要最小限の操作、得られる結果 |
| 60〜75秒 | 結果の画面 | 結果がどう困りごとの解消につながるか |
| 75〜90秒 | 結果の画面から短い締めカードへ | 顧客への提案の一言、重要な提供条件、詳細の参照先 |

120秒は余裕を含めた上限で、毎回埋める枠ではない。
短く伝わる場合は60〜75秒で終えてよい。
利用条件が価値の成立を左右する場合は、締めまで待たず、冒頭やデモにも短く添える。

## 台本とデモの組み立て

先に「[対象者]が[業務場面]で困っている時、[作業の変化]によって[価値]を得られる」と1文で書く。
この因果関係を実画面で示せる場面をデモに選ぶ。

デモは対象の画面を開いた状態から始めてよい。
メニューをたどる操作や長い入力は減らし、結果を数秒止めて見せる。
テロップは「確認先が1画面にまとまる」など、その時点で分かる変化を書く。
ナレーションはクリックする場所の読み上げに偏らず、その操作で仕事がどう変わるかを話す。

初稿のナレーションは全体350〜450字程度を目安にする。
話速や操作時間によって完成尺が変わるため、文字数では合否を判定しない。
実際の音声を生成して尺を確認し、完成mp4でも120秒以内か測る。
超えたら、周辺機能、設定手順、例外説明の順に詳細共有へ移す。
価値が成立するために必要な条件は削らない。

締めの提案例（同じ架空の例）:

> 入社準備の確認先が散らばっているお客様に、確認を一か所にまとめる方法としてご紹介ください。

セールスとCSの両方に別の長い説明を足さず、共通して使える一言を基本とする。
個別の提案トークや導入支援手順は詳細資料へ置く。

## 操作、ズーム、フォーカスによる視線誘導

実際に操作して仕事が進む様子を見せ、注目箇所が変わるタイミングで画面にも変化を付ける。
同じカードを長く映す構成に偏らせず、全体の位置関係、操作中の部品、操作後の結果を順に見せる。

- 最初は画面全体で位置を伝え、対象へカーソルを動かす。クリックの波紋と短い枠で操作箇所を示す
- 細かい数値や結果を読む場面でズームし、周囲を暗くするフォーカスで見る場所を絞る。一度に強調する対象は1つ
- シーンの目安は5〜10秒。操作、結果、比較など意味のある区切りで視点を変える。長い説明は画面を変えるか台本を短くする
- ズーム中は結果を見せ、次の操作前に `h.unzoom()` で戻す。画面全体とのつながりが分かるよう、寄った後は適宜引きに戻る
- 操作直後の結果は数秒止める。読ませる時間を残し、意味のないカーソル移動やズームの往復で尺を埋めない

操作シーンでは `h.moveTo`、`h.clickAndClear`、`h.scrollTo` を使い、見せる場面では `h.hl` と `h.zoom` を使い分ける。
拡大率は対象の大きさに合わせ、文字や関連項目が画面の外へ切れないか静止画で確認する。
枠とテロップが大事な情報に重なっていたら、位置かタイミングを変える。
切り替えと演出の秒数も完成尺に含め、120秒以内に収める。

## 作成依頼に添えるコンテキスト

入力が不足していても、資料から分かる部分で下書きを進める。
中心価値や受益者が複数あり、どれを主役にするか判断できない時だけ質問する。
URL、権限、映してよい情報は、撮影へ進む前に確認する。

```text
セールスとCS向けに、リリース共有用の短い動画を作ってください。
目安75〜90秒、上限120秒。顧客に提供する価値を中心に、デモは1点。
操作と結果を適宜切り替え、ズームとフォーカスで見る場所を案内してください。
結果を読み取る間を残し、見ていて単調にならない構成にしてください。

リリース名：
根拠になる仕様・チケット・PR：
誰の（20字以内）：
どの業務（30字以内）：
どんな価値（30字以内）：
これまでの困りごと：
今回どう変わるか：
価値を示せるデモ場面と結果：
提供時期・プラン・権限などの利用条件：
詳細資料の参照先（なければ未作成）：

撮影URL：
撮影で保存してよい操作の範囲：
映してはいけない情報：
音声の希望：VOICEVOX（既定は四国めたん／ノーマル、話速1.05）
```

## 書き出し前の編集確認

- 冒頭だけで対象者、業務場面、得られる価値が分かるか
- デモの結果が、その価値の根拠になっているか
- 操作と結果の切り替えがあり、ズームとフォーカスで見る場所が分かるか
- 文字の欠け、強調の残り、テロップの重なりがなく、結果を読む間があるか
- セールスやCSが、どの顧客に何と言って紹介するか再現できるか
- 実測していない削減時間や、未確認の提供条件を断定していないか
- 詳細へ送った情報への参照先が、共有本文にもあるか

この確認は内容の評価であり、`demo.mjs check` による機械検査ではない。
